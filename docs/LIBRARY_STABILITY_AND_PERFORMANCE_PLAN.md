# 书库可靠性与长篇性能施工计划 / Library Reliability and Performance

拟定于 2026-11-12，更新于 2026-11-13。本计划承接 [ROADMAP](../ROADMAP.md)。S0 / S1 是旧版样本和打开失败恢复；S2 是独立 Windows 安装验收；S3 和 S4 分别优化正式写入和备份。候选验收不等于公开发布。

下一版先让作者确信“打开的是原来的书库”，并用真正的 Windows 安装器验证升级。之后再缩短打开一本书、采纳或修订一章的等待时间。不要求先重构全库，也不拿删除作者历史来换取性能。

## 顺序与交付

| 批次 | 交付 | 启动条件 |
| --- | --- | --- |
| S0 准备 | 从核实过的远端主线建立独立工作区，准备虚构旧书库 | 首个工程步骤；不改动原工作区 |
| S1 书库打开失败 | 保留原路径，显示恢复入口，不悄悄换到另一份可写书库 | S0 后；下一版必做 |
| S2 Windows 升级验收 | 在受支持的 Electron 上验证安装、升级、SQLite 读写和重启 | 可与 S1 并行准备环境；交付候选包前必须合并并验过 S1 |
| S3-A 打开项目 | 只更新当前项目的最近打开时间；保留排序 | 用 S2 同一套依赖先测基线，可单独合并 |
| S3-B 采纳和修订 | 只读取这次提交真正需要的记录，保留原有事务校验 | 沿用 S3-A 的样本；采纳、修订分别对照 |
| S4 历史与备份 | 按瓶颈选做：按需读历史、减少新记录副本或压缩自动备份 | 不阻挡前面发版；每项须有测量或明确的磁盘需求 |

## S0：选对起点

- 核查时 GitHub `main` 是 `78550db`。按 Git 的文件内容比对，当时本地 901 个非忽略项目文件均与 `v0.1.6-preview.20` 一致；与主线的差异只有 CI、依赖清单和锁文件。这是**拟定本计划前**的结果，不代表后来新增的文件都已发布。
- 开工前重新核对远端、未提交和未跟踪文件。从最新已核实的 `origin/main` 建独立工作区，带入这份计划及经确认的后续变更。保留作者原工作区，不硬重置，不用旧锁文件覆盖主线。
- 只用临时目录、虚构书库和模型替身。准备一份由 preview.20 写出的样本，至少含两本书、一章已采纳正文、一次修订和一条尚可续跑的任务。记录项目 ID、正文摘要值、版本链和已采纳草稿 ID，供后续逐项核对。不要复制真实书库做测试。

## S1：打开失败，不冒充空库

**preview.20 的问题。** SQLite 模块加载失败时，旧版可能切换为独立 JSON 并改写路径；文件缺失或损坏时，旧界面还可能显示可编辑的空项目列表。S1 将[打开与恢复](../src/main/LibrarySession.ts)分开：先完整读出所选库，再交给保存功能。读取已有库不建表，不用旁边的文件修复它；只有首次建库、明确新建或恢复才初始化文件。

| 情形 | 作者应看到 / 程序应做什么 |
| --- | --- |
| 真正首次使用，尚无书库 | 按现有流程创建默认库；已有合法旧 JSON 的首次迁移仍保留原件和备份 |
| 已选书库因磁盘未连接、路径失效、原生模块不匹配或读取失败而无法打开 | 显示出错的书库路径、简短原因及下一步；不改配置，不创建替代库，不开放对空数据的保存 |
| 用户要恢复 | 提供“重试”“选择已有书库”“从备份恢复”入口。先在所选位置验证能读，再切换；恢复优先写新位置。选择失败或取消，仍指向原库 |
| 用户明确选择使用 JSON | 保留 JSON 的独立使用及导入导出能力，说明写入哪个文件；不暗示新写内容会自动合回 SQLite |

不能只凭“文件不存在”认定是新用户。旧配置不足以区分首次使用和磁盘离线时，先请作者选择已有书库或明确新建。不要在判断之前调用会初始化空库的读取方法。

**验收：** 分别模拟模块不可用、已有库损坏及已配置的库暂时找不到；确认原数据库、配置和同目录 JSON 未被改写，也没有新建空库。恢复正常条件后点“重试”，两本书及版本链都在。另跑新用户首次启动、旧 JSON 迁移和显式恢复的正向用例。复用[存储验证](../scripts/validate-sqlite-storage.mjs)，并从成品窗口验证作者看到的状态，而不只看日志。

**复测入口。** [preview.20 虚构旧库](../scripts/fixtures/library-preview20/README.md)含两个项目、一次正式采纳、一次手动修订、一个可续跑的任务，以及原始 SQLite 和 JSON 备份的校验值。旧版和候选版只打开它的临时副本。用 `npm.cmd test -- validate-library validate-agent-library-choice` 检查选库、原件保护和 Agent 读写；用 `npm.cmd run qa:library:ui` 检查恢复页面和保存队列。成品窗口复测命令见样本说明，不能用开发预览或网页代替。

**S0 / S1 验收（2026-11-12，Windows x64）：**

| 验证范围 | 结果 |
| --- | --- |
| S0 起点 | 核对远端主线 `78550db`；在独立工作区保留两份计划文档，使用主线锁文件。未修改原工作区或作者书库。 |
| 旧版实证 | 在 preview.20 的独立窗口复现了 4 种误导性空列表：书库目录缺失、文件缺失、损坏且旁有 JSON、仅有损坏文件。 |
| 新版故障恢复 | 同一份样本分别模拟上述 4 种故障和原生 SQLite 组件不可用。出错时数据读写被拒绝，配置、原库和旁边 JSON 未被改写。恢复原条件后在同一进程重试，两个项目、正文、版本链和待续跑任务均与清单一致。 |
| 首次使用与作者操作 | 成品窗口分别验证首次建库、合法旧 JSON 迁移、选择已有库、将备份恢复至新文件、明确选择独立 JSON、明确新建；取消选择和选错文件不切库。所有窗口仅用虚构数据，未请求模型。 |
| 防止空备份覆盖 | 旧设置页的备份恢复及覆盖导入也检查完整书库结构。空对象、无效字节不能替代整库；有实际记录的旧项目片段仍可合并，支持带 UTF-8 BOM 的备份。 |
| 成品凭据 | 最终验过的候选 `app.asar` SHA-256 为 `4b235d3221f59c64f69a8dd7182a521f2e12e9eb296fb41053f8f65f0a9614ae`。11/11 种场景、23 个进程会话，模型请求为 0。 |

## S2：发布候选包必须过安装升级

preview.20 实包使用 Electron 39.8.10 / better-sqlite3 12.9.0；核查时主线锁定的是 44.9.1 / 13.0.3。按候选提交的锁文件和 [Electron 支持日程](https://releases.electronjs.org/schedule)复核，不把源码升级当成安装包升级。区分会随应用运行的依赖和只影响构建的依赖，不为清零告警一次合并所有大版本。

1. 在独立工作区安装锁定依赖，跑类型检查、全量测试和生产构建。从同一提交生成 **新版本号** 的 Windows x64 安装包，核对版本、SQLite 原生模块与 SHA-256。保留已公开的 preview.20 标签及附件。
2. 保留 CI 预览启动检查，并用 `npm.cmd run smoke:release` 检查实际 `win-unpacked`。后者不等于运行 Setup。另在干净 Windows 环境用 Setup 安装、启动，再验证卸载；第二条路径先装 preview.20、写入 S0 样本，再原地升级候选版。两条测试均不使用作者的用户目录。
3. 升级后核对原书库路径、项目 ID、正文摘要值和版本链；编辑样本一章、关闭再重开，确认写回同一 SQLite。独立验证 Node/Agent 仍能读取同一份样本。保留验收记录；任何一项失败均不发布，不用 JSON 回退冒充通过。

**回退：** 保留上一已验证安装包和升级前样本备份。先在隔离环境验证旧程序能否读取新版写过的样本；不能直接降级时，使用旧程序和升级前备份恢复到另一位置，不覆盖升级后的作者数据。S2 验收通过即可交付候选包，无须等待性能批次；对外发布另行确认。

## S3：按作者操作测量和修改

**先测，再改。** 沿用 [500 章基线及计时定义](./PREVIEW14_LONG_NOVEL_PERFORMANCE.md)和[虚构样本](../scripts/fixtures/long-novel-performance.mjs)。增加一档多项目、每章多次生成、采纳并非最后一次成功、含失败续跑与多轮修订的样本；目标约 150–200 MiB，以实际紧凑 UTF-8 JSON 字节数为准。这个数字是测试目标，不是真实作品统计，也不拿带缩进的备份大小与它直接相比。

在同一机器、同一依赖和同一份虚构库上分别跑改前与改后。记录启动到项目列表、点击“进入”到工作台可操作、采纳和修订到提交成功的耗时；同时记录每次操作的整库读取次数、跨进程传输字节和实体变更数。桌面操作建议先热身，再至少测 5 次，报告中位数、最慢一次和样本数；备份到期与不需要备份分开测。毫秒数用于对照，不设跨机器 CI 时限。

| 操作 | 改动入口与边界 | 可判定的完成条件 |
| --- | --- | --- |
| S3-A 打开项目 | [项目列表](../src/renderer/src/views/HomeView.tsx)当前为更新时间而等待整库保存。改为单项目更新，复用保存队列与版本冲突处理；导入后进入项目也走同一入口 | 在非备份日，打开已有项目不再为时间戳发送完整 AppData；除该项目和必要的存储版本标识外不改其他记录。重启仍按最近打开排序，并发编辑不被覆盖 |
| S3-B 采纳草稿、提交修订 | [SQLite 提交路径](../src/storage/SqliteStorageService.ts)目前两者都在事务内读完整库；生成步骤已有按任务读取的实现，不重写。列出校验实际用到的章节、版本、报告和回执，在原事务内按 ID 核对存在性及项目归属；保留独立的 Agent 授权校验 | 新旧实现对相同样本给出相同的接受或拒绝结果；常规提交不再读取无关项目历史。与当前正文不匹配的报告、过期版本和跨项目引用仍被拒绝；重复提交不增版本，中途报错不留半次修改，恢复后的正文一致 |

给每批保留一份同机对照：如果整库读取或传输没有下降、交互没有可重复的收益，先排查，再决定是否保留改动。不要因此删除校验、关闭备份或跳过存储版本检查。

## S4：有依据再减容

- **历史按需读取：先分读写，再减首屏。** [全量保存](../src/storage/sqlite/sqliteSnapshotWriter.ts)把输入缺少的实体视作删除。项目列表或历史摘要只能作为只读结果，不能补空数组后送回全量保存。先试一个入口：列表只拿概要，打开某章历史才取详情。回归场景是“不打开历史、编辑一章、保存、重启”，未加载的步骤、追踪、其他书的版本必须原样存在；全量 JSON 导入导出仍保留原语义。
- **优先减少新副本，不批量改旧回执。** 只在占用统计证实值得做时，让新回执引用不可变版本和对应报告；缺少可靠引用时保留快照。作者采纳的不一定是最后生成的那一稿，旧章节的修订前正文还可能只在[提交记录](../src/services/ChapterVersionChainService.ts)里。测试要能恢复旧版、查到当时的报告、续跑未完任务；不设“每章只留最后成功”规则。
- **备份先可恢复，再压缩。** [现有备份](../src/main/BackupService.ts)是未压缩 JSON。先让列表、识别和恢复兼容旧 `.json` 与拟用的 `.json.gz`，验证完整还原、坏文件和空间不足，再给**新自动备份**启用压缩。沿用自动备份保留 7 份的规则，只在新备份成功后轮替。保留旧版能读的普通 JSON 回退副本；不改手动备份和作品 JSON 导出，不自动清历史发行包。库外的 `.usage` 用量收据不随单个库文件恢复；密钥和授权不随作品备份搬运。

## 验证与交接

每个修改程序的批次运行 `npm.cmd run typecheck`、`npm.cmd test`、`npm.cmd run build`。S3 额外保留 [采纳](../scripts/validate-chapter-commit-bundle.mjs)、[修订](../scripts/validate-p2c-revision-commit-bundle.mjs)、[版本恢复](../scripts/validate-version-chain-restore.mjs)的对照；S4 压缩若启动，还要验证旧 JSON 导入导出、备份列表和恢复。性能记录只提交样本配方、指标与复现方式，不含私人路径、正文或密钥。不调用付费模型。

### Preview.21 实施记录

- **S2：** [Windows 双机验收](./S2_WINDOWS_QUALIFICATION.md)。以同一构建的安装包、两份安装报告和各自的冷启动回读作为依据，不用解包 smoke 代替安装升级。公开 preview.20 保持原样。
- **S3-A：** 界面携带项目 ID、所选书库路径与修订号，在原保存队列内更新时间。SQLite 只改目标项目及书库修订标记；JSON 后端仍需重写单文件。编辑时间不随打开项目而改变。
- **S3-B：** 采纳和修订在原事务内读取关联章节、版本、报告、候选与回执，并保留冲突拒绝及失败回滚。涉及全书计数的硬规则仍可读取当前项目的章节；不拿部分书库数据走整库保存。
- **S4：** 选择压缩新自动备份，不批量改写旧回执或裁剪生成历史。[备份实测](./S4_AUTO_BACKUPS.md)包含恢复、空间不足及超出解压上限的处理。虚构的 500 章样本保留占用从 541 MiB 降至 92 MiB，代价是到期写入中位数由 229 ms 增至 368 ms。启动读取整库仍是独立问题。

暂不安排流水线引擎搬目录、全库 CRUD 重构或清理作者历史。

## English summary

Start from a clean worktree based on verified upstream `main`. First distinguish an unavailable library from an empty one; preserve the original path and require an explicit recovery choice. Qualify a new Windows candidate with both a clean Setup installation and an in-place upgrade from preview.20 using synthetic data. Next benchmark and narrow two operations: updating the last-opened project and committing an accepted or revised chapter. Lazy history reads, smaller new receipts and compressed automatic backups are conditional; never submit a partial view as a full snapshot, delete an author's only recoverable version, or rotate manual backups automatically.

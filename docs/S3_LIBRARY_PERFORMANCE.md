# S3 书库性能：同机桌面对照

这份记录只使用合成书库。不打开真实作品，不调用模型，不运行安装器，不评价安装升级。测试源为干净的 S1 提交 `804f738`。S1 计时使用已验收的 `tmp/s1-final/win-unpacked`，改后只认本工作树的 `release/win-unpacked`；版本号变化本身不是 S3 已打包的证据。

## 结果

**未到期时，打开项目、采纳和修订分别比 S1 少等 72.5%、74.5% 和 98.1%（比较中位数）；启动没有提速。** 改后程序在本地从 `6563d15` 对应的生产代码打包，包含 S3-A/B 及 S4 自动备份。到期组测得的是这个组合成品，不是 S3 或 gzip 的单项效果。

| 操作 | 未到期 S1 | 未到期改后 | 到期 S1 | 到期改后 |
| --- | ---: | ---: | ---: | ---: |
| 启动至项目列表可用 | 1,882 / 1,989 | 1,957 / 1,990 | 1,924 / 2,382 | 1,921 / 1,975 |
| 进入已有项目 | 1,389 / 1,440 | 382 / 466 | 2,667 / 3,010 | 1,940 / 2,000 |
| 确认已审稿草稿至采纳成功 | 863 / 878 | 220 / 243 | 2,330 / 3,086 | 1,817 / 1,922 |
| 确认修订至正式提交成功 | 860 / 877 | 17 / 50 | 2,464 / 2,624 | 1,683 / 1,726 |

单位毫秒，每格为 **中位数 / 最慢一次，n=5**，均另有一次不计入的热身。启动尚未触发写入，两种备份条件下启动的小幅差异不能解释为备份成本。测量依次完成，未锁定系统后台负载；只比较本机本样本。17 毫秒接近两帧就绪检查的分辨率，不代表 SQLite 事务本身耗时 17 毫秒。

**未到期的逐操作诊断**（各 1 次，未参与计时）。箭头左为 S1，右为改后：

| 操作 | 整库正文读取次数 | SQLite 返回的实体 JSON 行 | IPC 请求字节 | IPC 应答字节 | 净变更实体 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 启动 | 1 → 1 | 30,921 → 30,921 | 0 → 0 | 172,845,392 → 172,845,391 | 0 → 0 |
| 进入 | 0 → 0 | 0 → 0 | 172,845,273 → 246 | 235 → 282 | 1 → 1 |
| 采纳 | 1 → 0 | 30,921 → 11 | 31,944 → 31,944 | 419 → 418 | 5 → 5 |
| 修订 | 1 → 0 | 30,923 → 6 | 46,922 → 46,922 | 363 → 362 | 5 → 5 |

S1 进入项目虽然未读取全部实体正文，但枚举了 **30,921 条集合/ID** 并接收完整书库；改后该枚举为 0，两版均只改变目标项目的实体 JSON。采纳和修订的 IPC 提交包大小没变，改善位于数据库校验读：改后仅返回 43,475 和 68,937 字节实体 JSON，带第二本书 ID 前缀的行从各 9,470 条降为 0。启动仍读完整书库并传给窗口；此处不能宣称已做历史按需加载。改后两项正式提交的结果、回执与正文均已回读；不是用减少写入冒充提速。

**到期时**，启动、进入、采纳、修订的整库正文读取次数由 `1/1/2/2` 变为 `1/1/1/1`；三个写操作都真实生成了备份。改后三项的 IPC 请求/应答及净变更实体数与上表一致，但备份各需读取一次完整库。仅看打开项目这一次，到期时 S1 自动 JSON 为 179,005,905 字节；改后自动 gzip 为 5,213,522 字节，**另有 179,005,905 字节的普通回退 JSON**。这次写出的两份文件合计 184,219,427 字节，不能把 gzip 单文件当成总磁盘占用。本档 720 章样本未测 7 份轮替后的长期占用；另见 [S4 的 500 章轮替实测](./S4_AUTO_BACKUPS.md#测量)。未到期的两版均已实证：单一兼容备份条目、大小、标识、修改时间及内容哈希未变。

**S4 取舍：** 若目标是减少打开列表的传输，值得先测只读项目概要：启动应答仍约 165 MiB，最大的生成步骤集合占 43.34%。若目标是减小新历史，两个回执集合合计占 24.54%，这是整个集合的体积，**不是可回收量**；早期采纳稿与后续修订链确有不同正文，不能用“留最后成功稿”代替历史。这些是下一次实验方向，不是已经测出的优化收益。

原始样本、42 个集合的字节数、SQL 形状及回读证据见 [S1 数值记录](../scripts/performance/s3-before.json) 和 [改后数值记录](../scripts/performance/s3-after.json)。包内依赖指纹一致；两版规范化依赖锁哈希均为 `785b1000108997831132713949eeadd955f0f5468c8dba4f8fd6809695392c2a`。S1 和改后 app.asar SHA-256 分别为 `4b235d3221f59c64f69a8dd7182a521f2e12e9eb296fb41053f8f65f0a9614ae`、`7727b338110c6e6cc25ca9f82304368e68cfe82154ebd6456661e99865a6572b`；同一 SQLite 种子为 `978c6f1da08db48ff3428c0e798e88f1896a1ce781494bb82f319183639a0946`。

## 样本与回读

种子 SQLite 文件为 190,050,304 字节；经 S1 存储服务保存并回读的 AppData，序列化为**无缩进 UTF-8 JSON** 后是 **172,845,159 字节（164.84 MiB）**。SQLite、JSON、自动备份是三种不同口径。配方使用已有长篇合成器，主项目 500 章，另一本 220 章；不是给小库追加无关填充文本。42 个数组集合合计 30,921 个实体。正式对照需要每轮复制同一份已关闭的 SQLite，而不是为两版分别造库。

| 集合 | 条数 | 紧凑 JSON 字节 | 整库占比 |
| --- | ---: | ---: | ---: |
| chapterGenerationSteps | 20,202 | 74,910,523 | 43.34% |
| chapterCommitBundles | 720 | 28,969,153 | 16.76% |
| chapterVersions | 1,800 | 16,162,133 | 9.35% |
| promptContextSnapshots | 720 | 13,739,653 | 7.95% |
| revisionCommitBundles | 360 | 13,442,541 | 7.78% |
| generatedChapterDrafts | 1,441 | 13,024,850 | 7.54% |
| chapters | 720 | 7,101,693 | 4.11% |
| generationRunTraces | 721 | 2,817,267 | 1.63% |

每个集合按 `Buffer.byteLength(JSON.stringify(array))` **实测**，包括方括号和逗号，不含集合键名；空集合为 2 字节。整库还包含设置、键名和顶层结构。完整明细随原始数值记录给出。合成文本重复有规律，其压缩率不能外推为真实小说的节省比例。

两个项目每章都有较早的采纳回执和之后生成的不同草稿；每四章有两轮相连的正式修订，每本另有一次失败中断。每轮先核对桌面实际使用的是本轮 SQLite，再从这份库只读核对：
- 两本书各抽第 4 章：回执仍指向较早、状态为 accepted 的草稿；回执正文与当时版本相同。后来的草稿属于另一个已完成的生成任务，正文不同、状态仍为 draft。两份修订回执前后正文衔接、父版本衔接，最终正文与第二份修订一致。
- 两个 unfinished 任务的失败步骤均为 generate_chapter_draft；之前有已完成且保留输出的步骤，之后有 pending 步骤。检查的是**保留续跑所需的记录**，没有实际调用模型续跑。
- 另外核对两个**通过窗口提交**的目标：主项目第 2 章走已审稿采纳，回执关联匹配的质量报告与编辑裁定；第 500 章接受一份有来源正文哈希的修订。各新增一份正式回执；两处正式正文、修订版本及候选状态均须与提交一致。

## 测量口径

Windows x64，Ryzen 7 7800X3D，16 个逻辑处理器，33,397,133,312 字节内存。两边均核对 Electron 实际版本 44.9.1、better-sqlite3 13.0.3、原生模块哈希及包内依赖文件指纹。锁文件核对 `lock.packages`：**只删除** `packages[""].version`，递归排序对象键、保留数组顺序，对紧凑 UTF-8 JSON 求 SHA-256。这样根包名称、依赖声明、传递依赖和完整性字段仍参与比对；不要求整个文件字节相同。

- **计时**：实际解包程序、全新进程和临时用户目录。每种备份条件各 1 轮热身、5 轮正式样本，串行；不清操作系统文件缓存。复制种子、造备份和读回都在计时之外。启动从生成进程开始，到列表显示两个项目且目标“进入”可用；打开从原生鼠标点击到工作台显示正确项目且导航可用。采纳和修订分别从最后一次原生确认点击到界面显示该次提交成功。条件连续两个动画帧成立。选择项目、导航、阅读、首次点击与最终确认之间的等待不计入提交耗时。
- **备份**：未到期时提供可读的合成整库 JSON，文件名为 `novel-director-<time>-auto.json`。每项前后要求目录条目、文件大小、文件标识与修改时间不变，整轮结束还要核对内容 SHA-256。到期组第一次写前无备份，后两次在确认前仅将本轮临时目录内的自动备份文件名时间戳调早，实际备份逻辑不变。每个写动作必须各新增一份自动备份；若产生回退 JSON，另列字节数。
- **诊断**：每版每种条件另跑一次，不使用诊断进程的耗时。解开该包应用内容，在临时主进程入口加载观测器；使用同版 Electron、包内 SQLite 和原窗口交互。记录实际被执行的整库实体 JSON 查询、其他 SELECT 结果行、实体 JSON 行数和字节、IPC 调用参数及应答。无条件读取所有 ID 但不取 JSON 不算读取整库正文。行数是交给 JS 的记录次数，不是磁盘页读取量；同一行被两次返回会计两次。变更数按操作前后所有实体 JSON 内容的 SHA-256 比对，包括新增；不把 meta.revision、设置表或相同实体的重复写入算作实体变更。
- **IPC 字节**：实际调用边界处的参数和应答分别序列化为紧凑 UTF-8 JSON 并计字节；不包含调用通道、事件对象或协议帧。这是**实际逻辑载荷的大小、线路流量的代理量**，不是 Chromium 结构化克隆或物理传输字节。无 IPC 调用不等于无进程内工作。
- **范围**：只覆盖此样本的成功路径和短期备份状态；不是所有校验分支、并发冲突、备份轮替、恢复和压缩率的验收。五次的最大值只是这五次里最慢的一次；不设跨机器门槛。

## 复现

从已获准使用、拥有同锁依赖和两个解包程序的工作树执行；先确保本地 S1 临时路径不存在：

```powershell
git worktree add --detach tmp/s3-perf-s1 804f738
node --max-old-space-size=8192 scripts/performance/s3-seed.mjs
# 用上一步输出的同一个 s3-seed-* 目录名替换 SEED。
node scripts/benchmark-s3-library.mjs before SEED timing
node scripts/benchmark-s3-library.mjs before SEED diagnostic
node scripts/performance/s3-evidence.mjs before BEFORE_TIMING_DIR BEFORE_DIAGNOSTIC_DIR
node scripts/benchmark-s3-library.mjs after SEED timing
node scripts/benchmark-s3-library.mjs after SEED diagnostic
node scripts/performance/s3-evidence.mjs after AFTER_TIMING_DIR AFTER_DIAGNOSTIC_DIR
```

参数中的目录只取末级名称。脚本不安装依赖、不构建、不修改原包。调试时可用 `smoke` 代替 `timing`，只跑一次未到期，不作为性能结论。小型结果记录不含本机路径或正文，整个大库无需纳入仓库。

### 优化什么，而不是继续增加什么

产品目标：作者或 Codex 能连续完成“想好下一章 -> 生成 -> 阅读 -> 修改 -> 采纳 -> 继续”，不必先理解全部内部模块。正文由工作台配置的模型生成，导演负责创作判断。普通表达、节奏和有争议情节应允许导演决定；只把数据写错、版本覆盖和保存失败当作必须解决的技术问题。

| 当前基础 | 本轮判断 | 实施方式 |
| --- | --- | --- |
| 配方、合并分析、当前正文绑定、事务采纳 | 已有可复用主干 | 测真实流程与最终采纳成本，不另建流水线或评分系统 |
| 现场改写、候选暂存、调用状态、Agent 修订 | 已有当前切片与历史包内验收 | 列为回归项；出现复现问题才修，不按旧计划再造一遍 |
| 候选接受/拒绝/编辑后接受与回执 | 已补可追溯的决定撤销；旧直接保存入口和时间线自动提取仍需核对 | 共享命令支持专项处理，不重复创建候选体系；旧记录没有前值时不编造撤销 |
| 任务契约和规则校验 | 能执行明确约束，但混有具体人物/情节规则和隐式数值解释 | 把作品特例移到任务或测试数据；没有明确依据的判断降为建议，不自动补写剧情要求 |
| 完整 AppData 保存与 SQLite bundle | 正式提交已事务化，普通保存仍有全量重写路径 | 先测高频保存，再优化一条热点；不因用了 SQLite 就认定性能问题已解决 |
| 人类页面与 Agent 工具 | 共享数据已有，操作完整度和项目授权仍需补齐 | 同一动作共用服务、结果和提交记录，不衍生第二份数据库或独立业务系统 |

### 交付顺序

以下是从当前已落地基础继续施工的顺序，不是重做 M1-M3。每批能单独试用；界面随该批功能一起交付，不等所有后端做完才改。

| 批次 / 工作包 | 核心交付 | 作者实际获得什么 | 完成标准 |
| --- | --- | --- | --- |
| 1 / W03 | 候选决定闭环 | 同一事件集中处理；可编辑后批量接受；已作决定可撤销 | 伏笔/时间线/角色候选入口齐全；撤销形成补偿记录，不删除历史；下一章读取决定后的实际事实 |
| 2 / W06 | 任务编辑与局部更新 | 改一处任务，不必重新生成所有内容；明确知道哪些结果需要更新 | 文风、篇幅、目标、角色、伏笔、正文、快照七类修改均有重建边界；普通小说不受特定作品规则干扰 |
| 3 / W07，回归 W02/W04/W05 | 正文优先的作者界面 | 看正文、判断和修改成为主流程；不必来回找页面 | 六条用户旅程可完成；紧凑窗口无遮挡；候选、正文编辑和正式版本的状态清楚 |
| 4 / W08 | 完整 Agent 导演闭环 | Codex 不看 UI 也能管理故事世界、修订和逐章连续生产 | 在作者授予范围内执行；每章审阅、决定、正式提交后继续；人类可在 UI 接手相同数据 |
| 5 / W05/W06/W10 | 生成质量与成本校准 | 减少重复调用和无效 Prompt，不靠削弱正文能力换速度 | 固定任务对照；报告最终采纳成本、返工和质量；收益不成立的改动不设默认 |
| 6 / W09 | 长篇性能优化 | 长小说编辑和切换保持顺畅 | 10/100/500 章隔离样本实测；只优化最高频热点；小粒度保存不丢版本、不改其他项目 |
| 贯穿 / W01 | 可识别的发行 | 知道打开的是哪一版、数据在哪里、哪些功能真的在安装包里 | 源码检查、包内验证和公开发布分别记录；安装包与试用说明对应 |

批次 1 的命令结构稳定后，批次 2 可并行；页面原型可以提前，正式按钮接稳定服务。Agent 随每个新动作补接口，批次 4 负责整条旅程收口。成本和性能测量可提前采集，不阻塞已经证明有用的交互改进。

### 第一、二批的具体施工边界

**W03：让“接受了一个建议”成为可理解、可修改的决定。**

1. 对照提取结果、Inbox、章节/伏笔页和 Agent，列出候选来源到最终写入的路径。缺的是入口就补入口，已有结构能表达就不新增 collection。
2. 沿用事件分组，展示原值、建议值和实际采纳值；支持选择组内部分条目，不把弱相关建议强制捆绑。
3. 为新决定保存必要的变更前后信息。撤销通过同一保存队列和事务命令生成补偿记录，并可重复请求而不重复执行。
4. 后续有人修改同一事实时，显示实际差异，让导演选择保留当前值或作出新修改。无关字段变化不应阻止撤销；依赖尚未厘清的创建记录不能直接删除。
5. 旧回执没有足够历史信息时，明确显示无法自动还原，并提供查看来源和手动修正入口，不能猜测原值。

主要边界：`CandidateDecisionService.ts`、`candidateDecisionAmendments.ts`、`DecisionInboxService.ts`、`views/inbox`、存储候选命令与 Agent 工具。验收重点是重复决定、部分组选择、后续编辑、事务失败以及 UI/Agent 对同一事件得到相同结果。

**W06：让本章任务成为可编辑的创作输入，而不是只读报告。**

1. 默认编辑目标、冲突、出场角色、伏笔动作、结尾和表达要求；高级字段可展开，空字段不要求填满。
2. 修改文风只重组表达部分；修改篇幅先调整预算；修改目标/角色再补选相关资料。复用现有计划后二次补全，不从零建立通用依赖图。
3. 正文变更后重审当前版本，旧正文及旧报告作为历史保留。修改任务不会自动丢弃已生成候选，也不自动发起新的付费生成。
4. 清理 `ChapterTaskContractService.ts` 的作品专属人物规则；隐式收尾长度等解释只有在任务明确配置时才作为硬条件。保留原有复现用例，同时加入换人物、换题材和否定语境的对照用例。
5. Prompt 用正向目标、关键事实、少量独特限制指导写作。同类规则按适用范围合并，不能只凭词语相似删掉例外。伏笔十条是上限，允许本章一条旧伏笔也不推进。

主要边界：ChapterTask 与现有任务生成入口、`ChapterTaskContractService.ts`、`PlanContextGapAnalyzerService.ts`、Planner/Budget、Prompt formatter 与快照。验收矩阵沿用 1.13 G，不让运行中配置或用户快照被静默改写。

### 衡量收益

下面是施工目标，不是已经测得的结果。第一批先记录现状；门槛按同机、同构建和同任务比较，不以不可靠的绝对数字卡住发行。

| 指标 | 目标与记录方式 |
| --- | --- |
| 作者操作成本 | 记录六条旅程的必要点击、页面往返与重复填写；重点旅程力争降低 30%，但不隐藏影响来减少点击 |
| 模型成本 | 按最终采纳的一章累计规划、正文、审稿、修订与重试 usage；没有 usage 时标记估算，不预先承诺节省比例 |
| 创作质量 | 对照人物动机、衔接、伏笔边界、可读性与人工返工；少一次请求但多一次整章重写不算收益 |
| 可恢复性 | 隔离用例验证切页、重启、取消和失败后候选仍可继续；正式操作幂等，旧版本保留 |
| Prompt 有效性 | 记录必要事实覆盖与独特约束保留；任务/事实/重复限制的组成可查；不以单纯变短作为通过标准 |
| 长篇响应 | 使用现有性能脚本及隔离 fixture，预热后多轮记录 p50/p95、规模和环境；先测保存和项目切换，再决定优化范围 |
| Agent 效率 | 记录一章的工具往返、读取 token 和是否需要 UI；compact 为默认，导演需要时能获取完整资料 |

文学效果对照至少覆盖开篇、日常推进、战斗、揭露、高潮和复杂关系章节。少量样本只能作方向判断，不能宣称普遍提质。远程实验在明确模型、样本和费用预算后单独执行，本次计划不触发调用。

## 一、计划目的

Novel Director 已经具备完整的长篇小说生产基础：结构化上下文、角色状态账本、伏笔调度、剧情导向、HardCanon、章节计划、正文生成、质量门禁、修订、版本链、SQLite 事务、Run Trace 和 Agent Runtime。

下一阶段不再以“增加更多防错规则”为主。核心目标是把现有能力组织成一个更快、更顺、更有创造力的导演工作台：

1. 减少每章不必要的模型调用和重复 token。
2. 让作者从“理解系统模块”转为“完成下一步创作决定”。
3. 让 Prompt 更像导演指令，而不是规章汇编。
4. 让局部修订、候选确认和章节采纳更自然。
5. 让 Codex Agent 与人类导演共享相同的信息权和操作能力。
6. 在不推翻现有 AppData、SQLite 和版本链的前提下改善长期扩展性。
7. 用真实接受率、修订次数、耗时和 token 数据评价优化结果。

### 1.2 执行摘要：先完成什么

未来三个可发布里程碑只围绕一个目标展开：让作者从“打开项目”到“得到可接受的新章节”形成一条连续路径。使用 M1-M3 表示交付结果，不提前绑定版本号；版本号在发行验收时确定，不表示产物已生成。

| 顺序 | 发布目标 | 必做范围 | 暂不夹带 |
| --- | --- | --- | --- |
| M1 | 可靠完成一章 | 当前报告与采纳一致、运行取消/恢复、候选不锁死草稿、源码与安装包能力一致 | 新页面、FTS、数据模型重写 |
| M2 | 更快地改好一章 | 既有模型路由与综合审稿验收、质量问题直达修订、选区对比与恢复、调用级等待状态 | 新检测维度、固定多模型复审；不等待大型 A/B 才交付交互改善 |
| M3 | 连续创作闭环 | Decision Inbox 收口、主动作贯通、任务书字段化、Agent 关键同权、逐屏可用性与新手路径 | 复杂图表、完整关系型重写 |

高频小粒度写入、项目查询和长篇检索在后续批次独立交付，不阻塞上述三个版本。Agent 能力随每项作者动作同步接入，不等待某个远期版本才获得信息权和决定权。

当前唯一最高优先级是批次 C。除发布阻断缺陷外，任何新增检测规则、顶层页面或数据 collection 都必须证明它能缩短作者完成一次“生成 -> 审阅 -> 修订 -> 接受”的路径，否则延后。

### 1.4 六条用户旅程

全盘优化以以下旅程验收，而不是以新增页面、接口或验证脚本数量验收：

| 旅程 | 理想操作 | 需要交付的变化 |
| --- | --- | --- |
| 第一次写作 | 配置一个可用模型 -> 写一句章节想法 -> 生成第一章 | 标注哪些资料可选；空 Bible、空账本不触发表单补全竞赛 |
| 日常续写 | 打开项目 -> 继续下一章 -> 审阅 -> 接受 | 一个明确主动作；默认继承模型、篇幅与导向；内部步骤不占主视图 |
| 结果不满意 | 选择问题或直接写要求 -> 对比候选 -> 应用 -> 继续阅读 | 不必先有门禁问题；保留未选段落、阅读位置和可恢复版本 |
| 更新故事世界 | 看一次故事变化 -> 批量或逐条决定 -> 继续 | 不在记忆、角色、伏笔页面重复确认同一事实；pending 候选不封锁正文 |
| 交给 Codex | 读取项目 -> 逐章计划/生成/审稿/修订/提交 -> 汇报 | 可请求 5/10/几十章，不限 2-3 章；每章提交成功后再进入下一章 |
| 换电脑或升级 | 导出 -> 安装新版 -> 导入 -> 打开并继续 | 数据路径清楚、版本可识别、项目与版本链完整；不要求作者理解 native ABI |

### 1.6 少防御、强控制的具体取舍

| 不再默认这样做 | 改为这样做 | 仍保留什么 |
| --- | --- | --- |
| 一般编辑建议逐层确认 | 非阻断建议就地展示，作者可接受并继续 | 正式提交前展示本次写入对象和当前正文版本 |
| 有 pending 候选就不能采纳 | 章节采纳与长期状态决定解耦，接受后给“处理候选 / 下一章” | 正文明确依赖、且尚未确认的关键状态用具体证据提示，不把全部 pending 升级为 blocker |
| 新人物、新规则一律判风险 | 区分既有依据、任务许可和真实无来源救场；低置信度只提醒 | 新硬设定是否写入长期账本由授权范围控制 |
| 所有功能先补齐资料才能用 | 先写起来，缺什么在用到时再补 | 不编造缺失字段，不把空模板发送给模型 |
| 一次失败重跑整条流程 | 复用匹配的成功产物，仅重试失败步骤 | 已消耗的模型请求如 provider 无幂等机制，不承诺绝不重复计费 |
| 每章都做全面双重审稿 | 标准合并、严格可选、出现具体风险才升级 | 新模式只适用于新 run；旧快照和配方仍可复现 |
| 为了提速自动关闭所有思考能力 | 让正文/规划角色的能力配置可见，基于 A/B 决定默认值 | 已有 provider 兼容策略继续保留，不能偷偷改变用户设置 |
| 每发现一个问题就新增页面或类型 | 优先在当前正文、任务、证据和共享动作中解决 | 仅在确有持久化身份或复用价值时增加结构 |

创作权限不是技术完整性的替代品。作者可以决定保留一个有争议的情节，不能让一次旧版本覆盖写入被伪装成成功；这两类情况的提示、按钮和错误返回必须分开。

| W04-b 不浪费已生成的文字 | 验收已有超范围候选保留与整章接受；补重新选段、来源过期后的重定位与继续修改，复用现有 revision session/version | 作者可以看、挑、再改，而不是只能重试；第一次修订前的原文也能在版本历史中找回 | 局部请求返回整章；正文已改但候选迟到；重复证据不能自动定位；重新定位只替换确认片段；首次修订可恢复 |

| W05-b 实际参数说清楚 | 在现有角色 profile 中展示实际发送的模型、输出上限、超时与能力开关；官方 DeepSeek V4 的固定兼容策略改为可解释、按能力支持的选项 | 知道本章究竟由哪个模型、哪种能力生成；正文能力选择与提取/审稿速度选择分开 | 保存设置和单次覆盖一致；旧 run 冻结不变；不支持的参数不盲传；调用 trace 记录实际配置且无密钥 |

首批顺序：W01-a 建立可测基线 -> W02-a 明确作者决策 -> W03-a / W04-a 依共享命令稳定程度交付；W05-a 可并行。对共享保存队列、类型和调用协议的修改由同一个集成人员协调。计划不要求启动多个代理，也不擅自调用付费模型或上传发行产物。

每张卡的验收使用三个状态：

- **通过**：行为测试和对应真实页面路径有证据，记录 build 与结果位置。
- **部分通过**：代码存在或单服务测试通过，但 UI、Agent、存储或发行环节尚未闭合。
- **未验证**：只有规划、代码阅读或历史报告，不能对用户宣称已经修好。

只有本批的实际缺陷阻止本批发布。不用“必须全盘重构完”拖延可用性改善，也不用一次成功运行掩盖尚未验证的边界。

### 1.8 明确由谁做决定

| 情况 | 默认体验 | Agent 行为与授权 |
| --- | --- | --- |
| 普通场景细节、对白、合理的新信息 | 允许创作，不要求为每个细节补设定 | 与作者同样可决定，不因检测关键词就暂停整章 |
| 文风、节奏、低置信度疑似新人物 | 提示证据和修订建议，可保留正文 | 可判断忽略或修订，记录简短理由，不伪装成人类操作 |
| 重要新规则、不可逆角色状态、HardCanon 写入 | 一次影响预览后由作者确认；正文采纳和硬设定入账分别决定 | 当前高风险人审默认保留；后续由作者在 UI 明确授权项目/动作范围，再允许 Agent 在该范围内决定。Agent 自填 `confirmedHighRisk` 不等于人类授权 |
| 旧版本覆盖、错误项目引用、事务失败、无法解析的提交 | 保留草稿并给恢复动作，不能把技术失败显示成成功 | 同一规则，不用“导演权限”绕过数据完整性 |
| 连续生产 5/10/更多章 | 按标准单章流程逐章完成，上一章正式提交后才推进下一章 | 不设置任意的 2-3 章上限；遇到授权外决定或不可恢复错误才暂停，并保留已完成章节 |

本轮只规划授权能力，不改变仓库现有高风险人工确认要求。未来实现时，作者可以撤回授权；撤回影响后续动作，不抹除历史提交，也不自动撤销已经采纳的章节。

三项需要特别纠正的体验，而不是增加门禁：

1. **继续修改的自由**：来源过期时保留旧候选和要求，允许重新选择最新片段继续；系统只阻止错误覆盖，不阻止重新创作。没有唯一证据时让作者选区或明确整章，不替作者猜。
2. **配置透明**：当前官方 DeepSeek V4 路径有固定关闭 thinking 的兼容策略。后续将此策略变为可解释的角色级设置，展示实际发送配置；在成对试用前不承诺开关对质量无影响，也不擅自改变旧 run。
3. **少确认不等于少信息**：普通创作建议直接可处理，正式采纳只展示一次必要影响；Agent 默认 compact，但完整正文、版本、报告和 Prompt 都按需可读。隐藏高级信息不能演变成剥夺导演判断依据。

### 1.10 施工与取舍机制

不同时启动十个大工程。始终保持一条作者主线、一条独立技术线：

- 主线：W02 -> W03/W04 -> W07，按一章的真实操作路径验收；W08 随对应动作一起补齐。
- 技术线：W01 建立发行基线；W05 改调用体验和观测；W06 做有对照的 Prompt 优化。
- 规模线：测量确实发现问题后再启动 W09/W10，不作为作者体验修复的前置条件。

执行规则：

1. 每次只领取一个可在隔离项目中完整演示的切片，例如“当前问题 -> 修订 -> 应用 -> 重审”。类型、服务、UI、Agent 与测试在该切片内一起完成，不分别交付五个无法使用的半成品。
2. 已落地代码先测缺口，不删除重做。未提交修改按来源保护；本计划不授权清理用户项目、覆盖数据库或自动发布 GitHub。
3. 开始时记录现有操作路径和至少一条失败复现；结束时记录新路径、截图、验证结果、剩余问题以及能否装包试用。
4. 对源码字符串断言，仅在行为保持且职责确实移动时更新。先写覆盖相同行为的测试，再删除被替代的冗余约束。
5. 未证实的审稿建议不得靠增加弹窗掩盖。已有正确性检查保留，但对应失败必须有明确恢复动作。
6. 远程模型 A/B 单独约定模型、样本与费用上限；本地 stub 证明流程正确，不证明文学质量。没有实际测量前，30% 等数字只作为探索目标。
7. 原则上每完成 W02、W04 或 W07 的可用切片即可形成试用包；版本号在发行验收后确定，不等全盘优化结束再让用户受益。

粗估工程量按 1.5 的区间累计约 22-38 个专注工程日，包含较多尚需进入任务后重新核对的工作，不是交付日期承诺。已有代码若验收通过可直接缩减；多人并行也不能省掉存储、UI、Agent 的最终联调。优先完成前三个可发布里程碑，不为了达到估算规模追加工程。

首次施工按以下具体差距收口，避免跳到下一轮架构设计：

1. **先建立可重复基线**：跑当前完整回归并分类失败；区分陈旧源码字符串断言、真实行为回归与 native 环境问题。不会为了得到绿色结果删除有效测试或更换用户数据库。
2. **补齐已有能力的调用方**：检查候选报告评估是否接到共享命令、旧 UI 与 Agent；检查单请求取消是否从实际按钮携带正确 run/call 标识。旧候选无新增字段、旧 bridge 缺新方法时应可解释地兼容。
3. **完成真实修订演示**：不只验证“进入修订页”；必须编辑候选、接受、从持久化数据重新读取，再恢复一次原文。未生成候选时修改要求和主按钮要在首屏可达。
4. **沿用同一场景发布验收**：源码通过后从相同基线构建产物，用隔离数据重做核心操作；包内版本、SQLite 与 preload 都正确后才称为可分发。

取舍规则：稳定复现的错误、明显多余的点击和丢失可用结果优先修；争议较大的新模型策略先做小样本比较。没有测出长篇保存或召回瓶颈，不启动 W09/W10 的大范围替换。某项优化增加步骤却没有改善作者判断，就缩减或撤回该设计，不追加另一层说明与门禁。

### 1.13 全盘执行安排：从功能齐全到创作顺手

总体判断：优先修复能力之间的断点，而不是继续增加能力数量。已有的配方、综合编辑结论、候选事务和版本链承担主干；新的工作围绕它们补少量作者动作。开发者能解释一次操作，作者能完成一次决定，Agent 能调用同一个动作，才算一个功能交付完整。

本次进一步核对了配方、采纳策略、PromptBuilder、导演主动作、保存队列、SQLite 保存、快捷候选和 Agent 修订定义。以下能力已经有实现，不应按旧表重新开发：

| 当前源码 | 已能确认 | 尚不能据此声称 |
| --- | --- | --- |
| `PipelineRecipeService.ts`、统一分析与语义审稿 | 有四种配方，fast 保留计划后二次补全，已有合并调用路径 | 所有章节都适合减少审稿，或固定调用数能保证质量 |

历史测试用于确认已有基础，不代替当前工作树和发行产物的验收。本次计划不新增“全部通过”或新的性能结论。代码存在、行为验证、包内验证、公开发布四个状态分别记录，完成后的任务不再作为下一轮新功能重复领取。

每行是一组可独立审阅的变更，允许拆成几个小提交。先补已有实现的缺口，不因为表里有名称就重新创建服务。依赖满足后，调用体验和页面样式可以并行。

#### C. 界面不是换色：逐屏改变操作方式

| 页面 | 默认呈现 | 移到次级入口的内容 | 必须方便完成的动作 |
| --- | --- | --- | --- |
| 项目列表 / 工作台 | 最近项目、正在写的章节、一个明确的继续动作 | 大量统计、历史运行、开发诊断 | 导入旧项目；恢复未完成工作；直接续写 |
| 生产流水线 | 当前阶段、正文或任务、三条以内主要结论及下一步 | 原始报告、完整 trace、内部十四步和配置细节 | 取消本次；从失败处继续；修订；采纳并下一章 |
| 章节 / 连贯阅读 | 居中正文、紧凑章序导航、选区操作 | 技术 ID、版本元数据、重复工具栏 | 跳章不打断阅读；选段改写；看差异；保留阅读位置 |
| 修订工作台 | 当前候选与原文对比、修订要求、接受动作 | 长篇来源原文、历史轮次、全量证据 | 没有质量报告也能主动修改；候选继续改；应用后回正文 |

| 角色 / 伏笔 / 硬设定 | 本章相关条目与可编辑状态，完整资料仍可访问 | 历史流水与不相关远期说明 | 修改事实或 treatmentMode 后清楚知道会影响哪些后续生成 |
| Prompt 构建器 | 本章任务、材料选择摘要、预算与缺口 | 全文 Prompt、每块 trace、全部模板字段 | 修正真正缺失的材料，不为了消除提示填满所有卡片 |

视觉统一使用正文优先、稳定列宽、克制分隔和一致状态色。技术细节可折叠但不能删掉；高级用户和 Agent 都保留信息权。短文本右键菜单不能成为唯一入口，选区工具栏或键盘也能触达同一动作。无需求不加大幅头图、套层卡片、动画统计面板或第二套导航。

不把“一个主按钮、三条摘要”等当作删功能的硬配额：复杂任务可以展开。目标是默认视图容易判断，完整能力仍然可用。逐屏检查 1280x720、1440x900 和较窄窗口，并覆盖长标题、长候选、空项目、失败状态与键盘焦点。

#### D. 每章成本怎么测，避免优化错方向

测量单位是“最终愿意采纳的一章”，不是一次成功 HTTP 请求。分别记录模型等待、程序处理、作者操作、修改轮次以及全部生成/诊断/重试 usage。Provider 不返回 usage 时标明估算，不给虚假的账单结论。

| 实验 | before / after 固定什么 | 先判断什么 | 再判断什么 |
| --- | --- | --- | --- |
| 合并复盘 / 审稿 | 同一任务、上下文、模型、参数和最终接受标准 | 是否增加漏检、丢失状态提取或导致更多修订 | 逻辑调用、实际请求、总等待与 token |
| Prompt 去重 | 同一任务与必要事实，保留独特约束和来源 | 人物动机、硬状态、伏笔边界和续写质量 | 重复限制与低价值回顾减少多少 |
| 正文能力 / 模型角色 | 配置可见；旧 run 不变；明确实际发送参数 | 是否更愿意接受正文，是否需要更多人工重写 | 速度、超时率与最终采纳成本 |
| 上下文召回 | 固定带已知关键事实的长篇样本与目标章节 | 需要的事实是否进入最终 Prompt，是否误带未来信息 | 选择耗时、预算占用与 trace 可解释性 |
| 小粒度保存 | 同机同构建、相同 10/100/500 章数据集 | 正文和版本不丢，UI/Agent 同步正常 | p50/p95 保存延迟、序列化量和无关更新 |

先做本地 fixture 和小规模对照，再决定是否扩大远程试验。采用第十二节的 12 组任务矩阵；少量文学评价只说明方向，不冒充统计结论。若某项减少 30% token 却增加一次整章重写，应判为收益不成立。个别效果实验没有明显收益，不妨碍独立的界面改善发布。

#### E. 明确合并、保留和延后什么

- **合并入口**：默认只呈现一份当前编辑结论，详细审稿仍保留；相同事件的候选集中决定，账本本身不混成一个文本字段。
- **合并请求**：优先复用已落地的统一提取、综合语义审稿及匹配当前正文的分析结果；不为了凑调用数省略必要的新正文重审。
- **合并操作**：普通采纳和覆盖提示一次说明；候选编辑加接受一次落盘；简单修订在正文现场完成。
- **保留自由**：可主动修订、保留有争议正文、选择未审稿采纳、查看完整 Prompt 和报告；“未审稿”不能被写成“通过”。
- **保留边界**：正在编辑的正文、目标项目、版本和提交结果必须准确；数据库失败不能伪报成功。这里保护的是作品，不是替作者决定剧情。
- **延后建设**：全关系型拆表、新全局状态框架、图谱、云同步、复杂可视化、通用插件平台。FTS 只有在现有召回确实不足时才做。
- **不再按文件长度分配迭代**：超大文件只有在阻碍本次修改或实测有性能问题时拆分；测试按行为保护，不为满足行数阈值制造更多转发层。

#### F. 可投入多少，怎样算完成

W01-W10 原估算合计约 22-38 个单人专注工程日，仅表示整套工作量范围，不是从今天起的日历承诺；已有代码可减少实施量，集成和真实试用可能增加验收量。每个里程碑开始时按当前差距重估。多人或模型并行不按人数直接除以工期，共享类型、保存队列、端到端验收仍需集中完成。

每个里程碑交付：可试用构建、实际行为变更、一个完整旅程演示、对应回归结果和未完成项。只改文档跑链接/编码检查；改业务跑针对性测试、typecheck、完整 test/build；准备分发再验收 unpacked 与安装包。不得沿用历史通过记录充当新包结果，也不必把无关长期研究绑成当次发布门槛。

第四批 W04/W05/W08 已完成本地试用验收，当前进入 W03 专项候选与 W06 任务编辑；W01/W02 和第四批能力作为既有基线回归。这里的顺序替代早期“从头做 W02”的安排。不直接铺开十个工作包同时重构。

#### G. 将任务变化变成局部更新，而不是整条流水线重来

这是 W06 的具体施工表。复用 ChapterTask、现有计划后二次补全和运行快照，不先造通用依赖图或缓存框架。修改影响的是下一次执行；正在运行和已完成的历史记录保持可回放，旧结果仍可查看和采用。

| 作者改了什么 | 应更新的部分 | 应保留的部分 | 交互与测试要求 |
| --- | --- | --- | --- |
| 文风、表达禁忌 | 后部 StyleEnvelope、相关写作限制和最终 token 估算 | 已选角色、伏笔及历史事实；若新文本使预算不足，再调用现有预算器 | 不重新做整库需求检索；不能把 style 改动当作人物状态变化 |
| 篇幅 | ChapterTask 篇幅、输出预算、总预算校验 | 当前计划和事实选择，除非作者要求重做计划或预算确实不足 | 提醒计划节拍可能过密，由作者决定是否重做；不偷偷切模型 |
| 本章目标、冲突、出场角色 | 任务书、相关 contextNeeds、补选与最终 Prompt | 不受影响的历史记录、原草稿、原审稿 | 显示“需要更新任务/上下文”，提供一个明确的重建动作；不自动发出付费请求 |
| 伏笔 treatmentMode、硬状态、HardCanon | 涉及该事实的需求与最终上下文；相关审稿标记为需复核 | 不涉及此事实的其他章节报告及历史快照 | 不因另一角色的无关编辑使整部小说失效；缺少依赖信息时解释需复核范围，不伪造精确判断 |
| 当前草稿正文 | 新正文绑定的审稿、Novelty、冗余及采纳结论 | 旧正文与旧报告作为历史，已完成的规划步骤仍可用 | 删除段落后旧证据不能在当前结果中复活；提供“重审当前正文” |
| 模型、超时或能力设置 | 新 run 或明确重试时的运行配置与 trace | 原 run 的冻结配置及已成功产物 | 展示实际发送配置；不能在后台把诊断模型换回全局默认 |
| 手动快照 | 新建或显式编辑的快照版本 | 原快照内容、选择和回放 | 不自动加入当前导向或新账本；提供“基于最新资料另建上下文”而非覆盖 |

实现顺序：先定义上述字段组与影响枚举，再接任务编辑页面；只对当前 run 计算影响，暂不建立全书实时追溯系统。完整重建继续保留为次级动作，不能成为每次小改的默认选择。

#### H. 让 Agent 同权成为可验收能力

M3 不以“新增多少工具”验收，而以作者动作能否通过同一服务完成验收。已有工具先复用，缺少的才补。下表是目标，不表示当前高风险授权已经实现。

| 作者动作 | Agent 应得到的信息与动作 | 共享结果 |
| --- | --- | --- |
| 了解项目并决定下一章 | compact 状态与下一章目标；可按需读取完整正文、任务、Prompt、版本和报告 | 同一份项目数据，不依赖截图，也不强制截断导演需要的资料 |
| 计划、生成和审阅 | 选择运行配方与角色配置，逐步执行，获得当前正文对应结论 | 同一 GenerationRun 和报告来源；内容生成仍由工作台配置的模型承担 |
| 接受或保留有争议正文 | 使用共享采纳预览与命令；未审稿状态与已有失败项诚实记录 | 同一 ChapterCommit、版本链和实际操作者，不以 `user` 冒充 Agent |
| 修改正文和恢复历史 | 创建修订要求、读取候选与 diff、应用或恢复 | 同一 RevisionCommit；每次恢复新增版本，不直接覆盖 |
| 管理候选与世界事实 | 接受、拒绝、编辑后接受，预览原值与最终值；读取完整来源 | 同一事实账本、receipt 和下一章 Prompt，编辑不能悄悄变更操作对象 |
| 连续创作指定章数 | 逐章计划 -> 生成 -> 审阅/必要修订 -> 决定 -> 正式提交，再进入下一章 | 不设任意 2-3 章上限；中途停止仍保留已完成章节与明确继续位置 |

授权只做项目级的简单范围设置，不引入复杂角色系统。作者可授予一批章节及指定世界状态动作的决定权；范围内不逐次打断，范围外给一个待决定事项。作品本身的创作判断开放，错误版本覆盖、跨项目写入和事务失败仍按技术错误处理。先接真实 actor 与共享命令，再开放项目授权，避免权限开放了但提交记录仍假装由人类完成。

#### I. 每批通用交付流程与后续启动条件

每批都交付一条作者能实际走完的路径，不交付一组孤立接口：

1. **建立隔离基线**：记录代码/构建身份与数据目录；生成、失败报告、修订通过、pending 候选和版本恢复使用同一组合成 fixture，不借真实小说测试写入。
2. **先测已有行为**：W02/W03 采纳和候选作为回归；本批新增路径单独演示，只修复实际失败环节。新增事实必须能被下一章上下文选到，而不只是卡片上显示成功。
3. **核对三端一致性**：UI 展示、存储中的提交、Agent 读取结果一致；重复点击/重放不产生第二条提交；无关 pending 不封锁下一章。
4. **交付试用构建**：运行针对性回归、typecheck、完整 test/build；随后测试生产构建与 unpacked。若分发安装包，再核对安装包身份和隔离安装运行，不能把 `build` 当作已经打包。
5. **试用后领取下一批**：当前 M2 收口后按 J 进入专项候选和任务编辑。不要继续扩充未审稿状态或新增评分维度，也不因为有长期研究未完就不交付已可用版本。

后续工作的启动条件同样明确：W09 在保存/切换的同机测量中确有瓶颈时进入；W10 先做小规模召回与作品对照，有收益再扩大。若完整 AppData 并非主要瓶颈，不为了“架构更先进”先改全部读写。付费模型实验单列样本和费用预算，不和本地 UI 验收混在一起。

阶段完成不要求每项研究都得到正结果。一个版本只要核心旅程更顺、数据与版本链不倒退、结果可被作者试用，就可以发布；不为了追求全盘零风险而无限延期。

#### J. 下一批可直接施工的任务卡

这些任务是上述全盘方案的当前执行入口，沿用 W 编号。规模是按当前差距估计的专注工程日，不是日历承诺；每张卡先确认前一批是否已经解决它。涉及同一共享类型或保存入口时先串行集成，独立 UI 和测试可并行。

| --- | --- | --- | --- |

执行更新：第 1 卡的当前切片已于 2026-09-06 完成本地 preview.4 验收，证据见第四批试用记录。下一张新增功能卡为第 2 卡 W03 专项候选与撤销，第 3 卡 W06 可在共享决定语义稳定后并行；第 1 卡保留为回归，不重复施工。未完成的真实安装升级、签名和公开发布继续单列。

第 1 卡完成即可交付一个试用版；第 2-4 卡构成下一组作者体验版本；第 5 卡补齐代理连续导演。第 6/7 卡不是前面发行的阻塞条件。无需等待一个“大而全”的版本才让用户体验改进。

**每张卡必须同时回答四个问题：** 作者少了哪一步操作？哪些已生成内容可以继续利用？UI 与 Agent 是否使用相同结果？测试及安装包是否证明了这条路径？若只能回答“文件更小”或“又加了校验”，应重新缩小或调整任务。

**本轮不再新增的负担：** 不强制填满角色卡，不要求处理完所有候选才能下一章，不让低置信度命名识别直接裁决剧情，不默认每章推进十条伏笔，不要求 Agent 为采纳 UI 候选先伪造改写。十条是上限，普通章围绕当前冲突选少量相关伏笔；没有必要时可以不推进任何旧伏笔。

**判断自由与数据正确分开：** 导演可以保留有争议正文，也可以在明确授权下决定新角色、新规则和设定修正；这些决定应带理由、来源和版本。项目错位、正文来源过期、写入失败不能靠“强制接受”掩盖，但系统应保留候选并帮助重新定位，不让用户重新生成一次来解决技术问题。

## 二、产品北极星

### 2.1 核心体验

作者打开项目后，应当在一个页面内看清：

- 小说目前进行到哪里。
- 现在最值得做什么。
- 最新草稿是否值得接受。
- 如果不值得接受，最关键的问题是什么。
- 点击哪个动作可以继续推进。

AI 或 Agent 接手项目后，应当通过结构化接口获得同样的信息，并完成与人类导演相同的标准单章流程。UI 和 Agent 只是两个操作入口，底层领域服务、事务提交和版本链必须一致。

### 2.2 成功指标

先记录当前构建的 before，再记录同一场景的 after。分开标记功能验收、设计目标与研究目标，不能把愿望写成实测结论。

| 指标 | 目标与计算口径 | 用途 |
| --- | --- | --- |
| 最终采纳一章的总成本 | 从确认本章任务到正式提交，统计全部生成、重试、提取、审稿和修订请求；另记人工修改分钟数 | 主要产品指标；不以少调用换取更多返工 |
| 标准单章模型调用数 | 正常路径按现有配方以 4 次逻辑调用为参考；实际 HTTP 请求、兼容降级与重试另计 | 观测；必要补审有理由即可，不硬卡次数 |
| 重复输入与等待耗时 | 先测可消除的重复部分，探索约 30% 改善；分别报告工作台处理、服务商等待与作者操作时间 | 研究目标，不作为首批发布承诺 |
| 首轮采纳率与修订轮数 | 同一组任务匿名比较，作者认为值得保留且返工量不增加；检查分数只作辅助 | 质量约束；小样本不声称统计显著 |
| 一次章节采纳 | 匹配当前正文的结果只做一次必要确认；pending 数量不决定按钮可用性 | 行为验收 |
| 恢复工作与问题修订 | Dashboard 一次点击恢复正确对象；有明确证据时一次点击打开已填要求的修订任务 | 交互验收，不把模型等待算作点击步骤 |
| 过期报告被当成当前报告 | 0 次；历史报告可以看，但不能冒充新正文的审稿结论 | 数据正确性验收 |
| Agent 完成标准作者旅程 | 不依赖 Computer Use；逐章完成计划、生成、审稿、决定和提交 | 能力验收，不按工具总数评分 |
| 高频保存 | W09 完成的正文保存路径不重写无关集合；10/100/500 章规模记录 p50/p95 | 局部交付验收，不要求先改完所有 save |
| Prompt 去重 | 同一适用范围的等价禁令单次表达，独特事实和 treatmentMode 边界不被误删 | fixture 与人工检查；不承诺通用语义判等 |
| 回归与发行 | 生成、采纳、修订、恢复、候选有行为验证，发布包另做隔离 smoke | 每批出口，不用历史通过记录代替本批结果 |

耗时比较固定机器、模型、参数与任务；价格未知时只报告 usage，不推算账单。数据一致性、版本链完整性是硬要求，跨机器 UI 时延和某个模型的一次文学评分不是硬门禁。性能优化未达探索目标时，可以交付已证明更好用的功能，不为凑数字删掉能力。

### 2.3 痛点到施工项映射

| 用户真实痛点 | 当前根因 | 对应施工项 | 最终验收信号 |
| --- | --- | --- | --- |
| 一章生成等待很久 | 历史重复调用已部分合并；当前仍需测 provider 等待、正文读取和重试占比 | P1.1-P1.4 | standard 正常路径以 4 次逻辑调用为预算；不重跑已成功步骤，实际 HTTP 请求数单独记录 |
| 生成结果返回空或超时 | 已有总 deadline 与运行配置；剩余重点是 provider 响应兼容、调用级取消与恢复体验 | P1.4、P7 | 空响应可恢复或给出明确失败；超时后从最后成功步骤继续 |
| 报告很多，但不知道该相信哪份 | 已有综合 verdict；需要验证全部入口都使用它，并减少默认展开的重复报告 | P1.3 | UI、Agent、采纳按钮只读取同一份当前正文编辑结论 |
| 修订后仍显示旧初稿风险 | 正文 hash 绑定已落地；关键上下文变化、旧数据及修订入口仍需联合回归 | P1.3、P3.2 | 正文或关键上下文变化后旧报告自动变为历史，不参与采纳 |
| 流水线步骤太多、状态难懂 | 四阶段已落地；阶段结束、待决定和正式提交之间仍需全入口体验验收 | P2.4 | 默认只显示四个作者阶段；技术步骤保留在高级区 |
| 首页不知道下一步做什么 | 页面按数据模块组织，而非按创作任务组织 | P2.1-P2.2 | 打开项目即可一键恢复当前最重要动作 |

| 伏笔、角色状态仍可能挤占或遗漏 | 需求、预算和实际最终 Prompt 的 trace 仍可能不一致 | P0、P6.1 | must 需求缺失可解释；最终 trace 以实际 Prompt 为准 |
| 修订工作台重、短文本修改绕路 | 局部修改和复杂修订共用重流程 | P3.1-P3.2 | 小修改原地完成，复杂问题一键带证据进入修订工作台 |
| 候选确认分散 | 记忆、状态、伏笔、时间线分别处理 | P3.3 | 一个收件箱完成接受、拒绝、编辑后接受，底层类型仍独立 |
| 项目变大后保存和加载变慢 | renderer 高频编辑仍可能传播完整 AppData | P4 | 高频章节/状态编辑改用小粒度事务命令 |
| Codex 仍需偶尔看 UI | MCP 已覆盖主链，但精细导演操作尚未完全同权 | P5 | 标准单章及多章循环不依赖 Computer Use |
| 测试多但定位慢 | 大量脚本串联，源码契约检查与行为测试混杂 | P7.1 | 单元/集成/E2E/发布分层，失败能定位到具体边界 |
| 打包版本与开发版不一致 | native ABI 与隔离 smoke 已有；源码改动不会自动更新历史安装包，需统一标识和发行验收 | P7.3 | 安装包 smoke 验证 SQLite、preload、导入和版本号 |

这张表是计划变更的入口。新增工作必须能对应至少一个真实痛点和一个可观测验收信号；否则默认不进入近期范围。

### 2.4 全盘优先级

| 级别 | 现在处理 | 判断标准 |
| --- | --- | --- |
| P0 发布阻断 | 空正文、超时不可恢复、旧报告参与采纳、事务/版本链错误、密钥或用户数据风险、安装包无法使用 SQLite/preload | 会丢数据、误提交、无法生成或无法发布 |
| P1 作者闭环 | Decision Inbox、问题直达修订、主动作连贯、任务书可读、候选不锁死草稿、窄窗口与焦点 | 每章都会遇到，直接影响能否顺畅完成创作 |
| P2 成本与规模 | 小粒度保存、项目级查询、上下文召回、真实 provider A/B、长篇性能 | 项目变大或连续生成时明显变慢、变贵、变不稳定 |
| P3 能力扩展 | Agent 高级编排、按需 FTS、效果实验、可选方案探索 | 核心闭环稳定后扩大工作方式；普通作者动作的 Agent 同权随功能同步完成 |
| Later | 图谱、复杂数据看板、云同步、插件生态、全关系型 schema | 不解决当前高频创作阻力，或会显著扩大维护面 |

优先级不是按“技术先进程度”排列。一个能减少两次页面跳转的改动，通常比增加一种新审稿维度更优先；一个能防止错误版本被采纳的修复，永远高于视觉润色。

## 三、设计原则

### 3.1 生成优先，阻断从严限定

把技术不可提交与编辑建议分开。下列技术问题暂停提交，必须先恢复有效数据或重新读取，而不是用“强制接受”绕过：

- 没有可提交的正文，或结构化响应不可恢复。
- 确认的正文与将要写入的正文不同，或目标章节已被另一入口修改。
- 事务提交或版本链校验失败。

**“没有当前报告”与“不能保存这份正文”不是同一件事。** 默认提供“重新检查当前正文”；同时规划明确的“直接采纳，未审稿”作者动作，保留未审稿标识与真实 actor，不伪造通过分数，不借用旧报告。Agent 是否能执行同样动作由项目授权决定。该动作是 W02 的后续增量，当前 `useDraftAcceptance` 仍要求匹配报告和完整 verdict，不能把目标设计当成现有行为。报告过期只让报告失效，不应让作者丧失修改、保留或决定自己作品的能力。

正文疑似截断、偏离字数或范围不匹配时，先保留可读结果并说明具体问题。可以继续写、转为修订候选或由作者手动接管；不能无证据宣称完整，也不把已有文字丢弃。

与上一章、HardCanon、不可逆状态的明确冲突，以及无来源的关键资源、知识或救场规则，默认建议先修订。作者确实选择保留时，用一次影响预览说明冲突与理由，形成可追踪决定；不串联多个内容相同的确认框，不自动把该情节写成新 HardCanon。Agent 是否可作同样决定由项目授权范围控制。

文风偏好、轻微节奏问题、一般冗余、低置信度新实体和可讨论的剧情选择默认只给建议，不阻断作者或 autonomous Agent 继续推进。

候选确认使用项目级授权策略，而不是永久固定为“AI 一律不能决定”：

- 默认模式继续由人类确认长期世界状态。
- 作者可以授权 Agent 在指定项目、章节范围和候选类型内处理低风险或明确事实候选。
- HardCanon、不可逆死亡、重大伏笔回收和世界规则变更默认不自动接受，但作者可通过带范围、期限和审计记录的明确授权放开。
- 无论由谁决定，候选来源、影响对象、理由和 commit 都必须可追溯、可撤销、可在 UI 中复核。

### 3.2 正向导演指令优先

最终 Prompt 优先回答：

- 这一章从哪里开始。
- 这一章要完成什么变化。
- 角色要做出什么选择。
- 读者在结尾应感受到什么。
- 哪些空间允许模型自由发挥。

禁止事项只保留与本章真实风险相关的最小集合，不重复发送通用规章。

### 3.3 UI 与 Agent 同权同源

所有正式操作通过共享应用服务完成：

```text
Human UI ---------+
                  +--> Application Commands --> Domain Services --> Commit Bundles --> Storage
Codex / MCP ------+
```

不能继续形成“UI 有完整能力，Agent 只能读和生成”的两套产品。

### 3.4 渐进替换，不做大爆炸重写

- 保留现有 AppData 完整加载和 JSON 导入导出。
- 保留现有 14 个内部流水线 step，先改变配方和展示方式。
- 保留现有 Commit Bundle 与版本链。
- 新增小粒度命令和查询，逐步替换高频完整保存。
- 旧 job、旧 snapshot 和旧报告继续 normalize，不要求一次性迁移历史数据。

### 3.5 视觉服务于判断，不服务于模块数量

界面采用安静、密集、可扫描的编辑工作台语气，不做营销式大卡片堆叠。统一约束：

- 一个页面只保留一个视觉主动作，次动作不超过两个。
- 正文、任务书、诊断证据和候选决定各有稳定阅读列宽，不让技术 JSON 抢占首屏。
- 同一状态只使用一种颜色语义：通过、注意、阻断、进行中、历史。
- 卡片仅用于可重复实体和真正独立的工具，不把页面分区层层套卡。
- 桌面宽屏优先提高信息扫描效率；窄窗口优先保证正文、主动作和当前阶段，不机械缩小全部控件。
- 图标、焦点、快捷键、右键菜单和按钮文案使用同一动作词汇；危险操作必须清楚说明可恢复性。
- 每个发布批次做 Dashboard、章节、阅读、角色、Prompt、流水线、修订、设置的真实截图 QA，而不是只检查 CSS 或组件渲染成功。

### 3.6 规则只在需要时出现

系统可以在后台保留完整诊断能力，但作者默认只看到与当前决定相关的证据。低置信度 Novelty、一般冗余、风格建议和候选提示不得占用与硬状态冲突相同的视觉权重，也不得无故阻断采纳。

## P0：Prompt 对齐与可测量基线

### 目标

先消除当前 Prompt 自身的结构矛盾和重复约束，并建立后续优化的可比较基线。

### 工作项

1. 让最终 Prompt 的物理顺序与优先级声明完全一致：
   - 写作任务声明。
   - 上一章 Bridge。
   - 本章任务契约。
   - HardCanonPack。
   - 角色硬状态。
   - 伏笔操作规则。
   - Story Direction。
   - 近期事实、远期摘要、时间线、风格。
   - 最小禁止事项与输出要求。
2. 修复重复编号和相同 priority。
3. 合并“禁止事项与 NoveltyPolicy”和“输出格式”中的同义禁令。
4. 删除未进入正文的 legacy block 占位，保留结构化 trace 说明即可。
5. 增加 Prompt 统计：
   - 每个 block token。
   - 正向任务 token。
   - 事实上下文 token。
   - 禁止/审稿口吻 token。
   - 重复语义数量。
6. 建立三组真实但脱敏的章节 fixture：日常章、规则危机章、揭露章。
7. 记录当前模型调用数、输入 token、耗时、首次通过率和修订次数。

内容层面补充三项，不再只检查 Prompt 是否够短：

- 任务契约优先明确“目标 -> 阻力 -> 角色选择 -> 局势变化”，字段未填写时仍跳过，不让系统编造剧情。
- 可推进伏笔 10 条是上限，不是每章应完成的配额。默认建议一个主要推进点和少量次要线索；作者/Agent 可按章节任务调整，hidden/pause 规则保持原义。
- 将自由发挥范围写清楚：普通动作、对白、场景细节允许创造；重大设定按任务许可处理。同样一句禁令不得在任务、伏笔分组和结尾护栏中反复输出。

- `src/services/promptFormatters/promptUtils.ts`
- `src/services/PromptLintService.ts`
- `src/shared/types/trace.ts`
- `scripts/validate-prompt-*.mjs`

- Priority Stack 声明与最终 block 顺序一致。
- 相同 Novelty 禁令不在两个区块重复出现。
- Prompt Guard 不删除有效剧情任务。
- 三组 fixture 均能输出可读的 block/token 报告。
- 原有 snapshot 和 pipeline prompt 继续可用。

## P1：自适应 AI 工作流与模型路由

### 目标

减少串行模型调用和重复正文传输，把严格审稿从“每章固定成本”改为“风险触发能力”。

状态：**核心实现已完成，等待真实 provider A/B 与发行产物验收。** 当前实现已覆盖配方、统一生成后分析、综合编辑结论、五角色 run profile 和调用遥测；在真实章节样本上确认质量与耗时后即可从施工主线退出。

### P1.1 流水线配方

复用已有 `PipelineRecipe`，校准行为与说明，不创建第二套配方：

| 配方 | 默认步骤 | 适用场景 |
| --- | --- | --- |
| fast | 计划、正文、必要检查、确认；本地优先是否适用按效果对照决定 | 低风险过渡章、作者快速试写 |
| standard | 计划、正文、统一复盘、综合审稿、确认 | 默认生产 |
| strict | standard + 独立一致性复核 | 高潮、揭露、规则密集章 |
| custom | 用户选择步骤 | 高级用户和调试 |

现有 PipelineMode 可扩展或映射到配方，不创建平行流水线。

当前 `fast` 虽跳过常规复盘和独立一致性步骤，`quality_gate` 仍通过 `DiagnosticsService` 注入 `QualityGateAI`，不能在说明里称它已经是“只有本地检测、只有两次模型调用”。W05/W06 先校准实际调用与文案，再决定是否增加明确可选的本地检查方式。切换方式时如实说明少了哪些语义检查，既不暗中多花一次调用，也不把少审稿包装成同等质量保证。

### P1.2 统一生成后分析

把当前章节复盘、角色变化提取和伏笔提取合并为一次结构化调用。返回：

- chapter review。
- continuity bridge suggestion。
- hard state candidates。
- soft character updates。
- foreshadowing candidates/status changes。
- timeline candidates。
- memory warnings。

原有三个 AI 方法保留兼容门面；新标准流程调用统一方法。解析失败时可以退回原拆分调用，但不能自动重复发送全部调用。

### P1.3 综合编辑结论

分两步收口，避免在决策语义尚未统一时先合并模型调用：

1. 先建立确定性的 `EditorialVerdict`：
   - 只读取与当前 draftId、正文 hash、任务契约和关键上下文指纹匹配的报告。
   - 聚合质量、一致性、Novelty、冗余和角色状态证据，但保留全部 sourceRef。
   - 同一问题只展示一次；`open`、`converted_to_revision`、`resolved`、`ignored` 使用共享生命周期规则。
   - `not_requested`、`unavailable`、`stale` 与“已通过”严格区分。
   - 合法 fast 配方不因未请求独立一致性报告而变成不可采纳。
   - 输出 blocker、advisory、证据、最多三个下一动作和 `canAccept`。
2. 再把标准模式的一致性审稿与 AI 质量判断合并为一次综合语义审稿：
   - 本地 Novelty、冗余、角色状态和任务契约检查只计算一次。
   - AI 收到结构化本地 findings，只补充语义判断，不重复机械检查。
   - 返回结构继续派生兼容的 ConsistencyReviewReport 和 QualityGateReport。
   - 仅在高风险、结果矛盾或 strict 模式下调用独立第二审稿。

`EditorialVerdict` 必须随 GenerationRunBundle 原子保存，并成为 Dashboard、流水线、采纳按钮、修订入口、作者摘要和 Agent 的共同决策输入。原报告继续保留为证据，不被新结论替代或删除。

### P1.4 运行级模型配置

新增可选工作流 profile：

- plannerModel。
- proseModel。
- extractionModel。
- reviewerModel。
- revisionModel。

默认全部继承当前模型，用户无需重新配置。一次 run 开始后冻结 provider、模型、超时、温度和 token 配置，重试继续使用同一快照，除非用户明确选择“更换模型后重试”。

实现时还必须覆盖：

- 正文、复盘、综合审稿和流水线内修订均从同一 run profile 解析配置。
- 每次调用记录 `runId / stepId / callId / role`，区分首次请求、重试和 response-format 降级。
- provider 返回的真实 usage 与本地估算 token 分开记录。
- 取消粒度下沉到单次 call，不能因为同一 run 发起复核而误取消另一个有效调用。
- 跨 provider profile 只保存凭据引用，不把 API Key 写入 job、trace 或 AppData。

等待体验单独验收：

- 区分排队、连接/等待首个响应、接收内容、重试退避、解析、保存，不用一个一直旋转的加载提示概括全部时间。
- 默认保留当前五分钟总预算，提供明确的本次预算与剩余时间。后续可配置首响应/空闲超时与总上限，但重试和格式降级不能偷偷重置总预算。
- 当前 HTTP 客户端会缓冲完整响应，不能把“请求尚未完成”显示成虚构正文进度。先交付真实耗时和阶段提示；流式正文预览作为可选后续项，半截响应只保存为恢复草稿，不能伪装成完整章节。
- 取消单次 call 与取消整个 run 分开；无关补审不取消正文请求。网络断开后是否值得重试由错误类型和已收内容决定，不因超时自动切换模型或降低创作能力。
- 模型能力与 thinking 配置按 provider 实际支持情况暴露；对现有 DeepSeek 兼容路径的性能策略做对照测量，不能把关闭思考描述为必然不影响质量。

### 验收

- standard 正常路径模型调用不超过 4 次。
- strict 仍能执行独立复核。
- 三类候选与 Bridge 不因调用合并而丢失。
- 所有报告继续绑定 draft content hash。
- 同一问题在编辑结论中只出现一次，但能回看全部来源证据。
- 未请求的可选报告不会被当成失败；真正缺失的必需报告不会被当成通过。
- 中途失败可以从最后成功阶段恢复。
- Run Trace 记录 recipe、每次调用的 profile、耗时和 token。
- 同模型、同 fixture 下报告端到端耗时、重复输入与实际 usage 的前后变化；约 30% 是探索目标，不是未经测量的保证。

其中前七项已由行为测试、类型检查和生产构建覆盖；最后一项必须用 DeepSeek / OpenAI 兼容 provider 的隔离数据实测，不用合成 token 估算冒充最终结论。

## P2：导演工作台与渐进式流水线 UI

### 目标

让首页成为可执行的创作入口，让用户无需理解全部模块也能完成下一章。

状态：**基础切片已完成。** Dashboard 主动作、导航分组、四阶段流水线、默认作者诊断和 Decision Inbox 首个切片已经落地；批次 C 重点补齐动作之间的连续性、窄窗口体验、键盘焦点和共享事务命令。

### P2.1 Director Next Action

复用已有纯规则 `DirectorNextActionService`，补齐动作目标定位，从现有数据推导最多三个动作：

- 继续运行中的 job。
- 重试失败步骤。
- 审阅最新草稿。
- 修订阻断问题。
- 处理待确认候选。
- 接受合格草稿。
- 创建或生成下一章。
- 补充真正缺失的角色状态或任务书。

建议不是一段文本，而是带目标页面、projectId、chapterId、jobId 的可执行 action。

### P2.2 Dashboard 改造

默认首屏展示：

1. 当前章节进度。
2. 一个主操作按钮。
3. 两个次操作。
4. 最新草稿和作者诊断摘要。
5. 待确认事项数量。
6. 最近编辑章节。

统计卡和“风险雷达”降为次要信息，不让提醒占据主要视线。

### P2.3 导航分组

保持现有页面，不删除功能，只分为：

- 写作：工作台、章节、连贯阅读、生产流水线、修订工作台。
- 故事世界：剧情导向、角色、伏笔、硬设定、小说圣经、时间线。
- 资料与高级：阶段摘要、Prompt 构建器、Agent 批次。
- 系统：设置。

Prompt 构建器、完整 step rail、Run Trace JSON 默认进入“高级”层。

### P2.4 流水线四阶段展示

14 个内部 step 聚合为四段：准备本章、生成正文、审稿诊断、审阅与决定。任务书规划和计划后补全归入准备本章。默认只显示当前阶段、耗时、结果和下一动作；点击“查看技术细节”才展示原始 step、context trace 和 JSON。

最后一段必须区分三个状态：

- `ready_for_decision`：流水线完成，等待作者或 Agent 决定。
- `accepted`：ChapterCommitBundle 已成功提交。
- `rejected_or_revision`：草稿未采纳，已进入修订或明确放弃。

内部 `await_user_confirmation` step 完成只能表示进入 `ready_for_decision`，不能让页面显示“已经提交”。阶段耗时从 step 的 started/completed 时间计算，不以任意记录的最后更新时间代替。

### P2.5 任务书与诊断阅读体验

- ChapterPlan 默认按字段显示目标、冲突、角色动作、伏笔边界、结尾钩子和允许/禁止新增内容，不先展示 JSON。
- 综合编辑结论位于诊断区顶部，只展示一句话判断、阻断项、建议项和最多三个动作。
- 质量、一致性、Novelty、冗余原报告作为可展开证据。
- Run Trace、Prompt block、context trace 和原始 JSON 只在高级区显示。
- 所有风险入口都能定位到正文证据或对应账本，不只显示抽象分数。

### P2.6 真实页面视觉修复清单

生产构建实测已确认页面可以加载，但下列问题应在批次 C 按作者频率处理：

1. 明确最小窗口策略：当前应用实质上以 1100px 为最低宽度。要么在窗口与文档中明确支持边界，要么提供 960-1100px 紧凑桌面模式；不能让横向裁切成为默认降级。
2. 生产流水线把“开始生成”放回配置面板附近，顶部仅保留状态和全局控制；未开始时右侧显示本次生成摘要，不保留大面积空卡。
3. 章节页在紧凑宽度将章节列表改为可收起抽屉、顶部选择器或限高列表，正文必须在首屏可见。
4. 修订工作台未生成候选时只保留一个主按钮；生成前使用“修订指令 + 原文预览”两栏，生成后再展开完整对比布局。
5. 设置页首屏聚焦模型和凭据；数据路径迁移已收入“数据与备份”折叠区，后续视觉 QA 只需确认紧凑窗口和键盘操作。
6. Dashboard 最近章节预览整体可点击或提供清楚的“继续编辑”，不能只把入口做成弱辅助文字。

视觉验收不追求所有页面外观一致，而追求动作层级一致：每屏主动作明确、正文区域稳定、错误与历史信息不会挤掉当前工作。

逐屏施工应交付明确的操作变化，而不是只换颜色：

| 页面 | 保留的主区域 | 减少的负担 | 完成标志 |
| --- | --- | --- | --- |
| Dashboard | 当前进度、最新草稿、下一动作 | 重复计数、空统计卡、模块介绍 | 一眼找到当前正在做的章节和继续入口 |
| 章节与阅读 | 居中正文、紧凑章节跳转、选区工具 | 永久占宽的大列表、多处滚动、反复跳回开头 | 读到哪就改到哪，应用后回到原文位置 |
| 生产流水线 | 四阶段、当前产物、一个主动作 | 技术步骤和原始 JSON 默认铺开 | 作者无需理解 step 名称也能重试、修订、接受和继续 |
| 修订工作台 | 原文、要求、候选；有结果后出现 diff | 无候选时的空对比栏、重复生成按钮、层层确认 | 打开即知道改哪里；一处对比后明确应用或放弃 |
| 候选收件箱 | 故事事件、涉及对象、本次变更 | 同义候选重复阅读、接受后还需去另一页确认 | 未处理项可追踪，已处理项不反复出现 |
| 设置 | 模型连接、常用生成设置 | 数据迁移、日志和高级路由抢占首屏 | 新手用一个连接完成首章，高级用户仍能展开完整配置 |

界面稿先在一条真实旅程中试用，再推广样式。不给每个功能增加必读说明；字段帮助、禁用原因和高级信息按需展开，按钮名称本身说明下一动作。

视觉施工采用现有编辑工作台风格的统一整理，不再反复整体换皮：

- 中性底色、清晰正文对比和一种主要动作强调色；红色只用于真正需要处理的问题，不让普通建议呈现为满屏报警。
- 导航、工具栏、正文、辅助信息四层稳定布局。阅读居中，列表可收起，诊断默认摘要；普通页面不嵌套多层浮动卡片。
- 章节选择、返回原阅读位置、右键选区操作和主提交动作优先于装饰。浮层以视口定位并避让边缘，缩放或滚动后仍跟随当前上下文。
- 提供一致的保存中、已保存、等待决定、需要修订、失败可恢复状态。错误旁边给出可执行动作，不只展示内部 exception。
- 首轮 QA 覆盖 1440x900、1280x720、1100px 最小支持窗口，以及 125%/150% 系统缩放和长中文标题。960px 紧凑模式是可选增量，不在尚未验证时宣称支持。
- 新手只需完成模型连接与首章想法；角色卡、Bible、伏笔、HardCanon 按需补充，在相关字段旁说明何时才需要，避免新增强制向导。

### P2.7 首次使用与材料分工

不要把首次使用设计为填完整套表单。默认路径是“连接模型 -> 创建项目 -> 写一句想法 -> 试写 -> 阅读与修改”，高级材料在真正用到时再补。

| 内容 | 何时需要 | 首次使用的处理 |
| --- | --- | --- |
| 模型连接 | 远程生成前 | 展示实际 provider、模型与连接结果；普通 API 和 Codex CLI 作为两种清楚的入口 |
| 本章想法 | 想控制本章发生什么时 | 接受短句，可生成可编辑任务书；不要求作者懂内部字段 |
| Story Bible | 需要长期背景和风格时 | 可空；不把长篇百科复制到每次写作 |
| 角色卡与状态 | 重要人物、资源、伤势和知识开始影响行动时 | 先建相关字段；从已采纳章节产生的候选进入同一收件箱 |
| 伏笔 | 需要持续铺垫、延迟解释和回收时 | 可空；区分本章推进与禁止揭示，不把 10 条上限做成填满指标 |
| HardCanon | 已明确不能随意改写的规则或身份时 | 手动少量维护，不要求补齐分类，也不自动提升 AI 输出为硬设定 |
| 剧情导向 | 作者希望影响未来 5/10 章时 | 可选软目标；不用每章重填，不覆盖已发生事实 |

教程与界面同步：用一个可公开的合成示例演示模型配置、哪些材料可以留空、一次局部修订、一次候选处理和继续下一章。不要新增强制教学弹窗；帮助放在可展开说明或教程入口，不占正文区域。

### 验收

- 打开项目后无需切换页面即可继续上一项工作。
- 正常章节从 Dashboard 到生成开始不超过 2 次点击。
- 低风险章节完成后主界面只有一个清晰主动作。
- 所有旧页面仍可从导航到达。
- 高级信息不被删除，只默认折叠。
- “流水线完成”“等待采纳”“正式提交”在文案和状态上不会混淆。
- 任务书与编辑结论在默认视图中无需阅读 JSON。

## P3：正文现场修订与统一候选收件箱

### 目标

让小修订留在阅读和章节现场，让复杂修订进入工作台；让所有“是否写入长期世界”的决定集中处理。

状态：**现场修订基础版与 Decision Inbox 首个切片已完成。** 共享候选事务命令及 `EditorialRevisionRequestService` 问题直达入口已出现于工作树，按代码已落地处理，完整验收另行记录；剩余工作包括专项候选覆盖、编辑后接受、撤销和真实入口到写回的闭环。记忆候选本身已可承载部分伏笔/时间线 patch，不能重复新建同义候选 collection。

### P3.0 共享 Application Command Kernel

在扩展候选收件箱和新的正式写入前，复用并补齐已有候选命令、提交服务和保存队列。下图是共同执行约定，不要求额外建立一个通用命令框架：

```text
preview -> validate expectedRevision -> apply domain service
        -> transaction/fallback save -> compact result + newRevision
```

每个命令统一携带 `actor`、`reason`、`idempotencyKey`、`expectedRevision` 和影响摘要。UI 与 Agent 调用同一命令，不各自复制候选接受、修订提交、状态写入和 HardCanon 变更规则。第一批只覆盖批次 C 实际使用的候选决定与修订动作，不先抽象所有 AppData CRUD。

`actor` 至少区分 `user | agent | system`；Agent 提交不能继续伪装为 `acceptedBy: user`。旧 commit 缺 actor 时 normalize 为 legacy/unknown 展示语义，不反向改写历史。

### P3.1 Inline Revision

状态：基础版已完成，后续重点是候选对比、失败恢复和报告失效范围。

章节页、阅读页和修订工作台共享同一套选区修订：

- 空白重写。
- 去 AI 味。
- 强化对白。
- 压缩节奏。
- 增强冲突。
- 自定义要求。

结果以原文/候选并排显示，并支持：

- 接受当前选区。
- 接受全部。
- 再改一次。
- 放弃。
- 一步撤销。

应用时创建 RevisionCommitBundle 或可追溯的编辑版本，不直接覆盖版本链。

候选的生命周期与自动替换资格分开：

- 正常局部结果：原文/候选比较，作者选择应用。
- 返回整章或范围不明确：保留候选，不能自动替换选区；可复制、重新选段或转整章对比。
- 来源正文已变化：旧候选继续可读，提供在最新正文上重新定位与再改；位置不唯一时由作者选择。
- 后端迟到结果：存入原来源关联的候选，不改变当前正在阅读的章节，不自动应用。

范围异常只影响应用方式，不应丢失一次已完成的生成。第一版复用 revision version 的正文与风险记录；只有现有字段不足以表达来源时再加最小字段，不新建一套候选库。撤销仍是新的补偿版本，不回退整个项目快照。

### P3.2 质量问题直达修订

从当前 EditorialVerdict 收口 Quality/Consistency/Novelty 的“修这一处”动作，复用已存在的修订请求服务，自动带入：

- 当前正文 hash。
- 证据片段；仅在当前正文唯一匹配时定位选区。未来补 offset 时与正文 hash 一起校验，不能拿旧偏移修改新正文。
- 推荐修改要求。
- 最小相关上下文。

修订完成后重新运行必要诊断，不整条重跑生成流程。正文 hash 变化后旧综合报告先标记为历史；只有能证明依赖范围未变化的局部结果才可复用计算，不能仅凭“改动很少”把旧报告标成当前。重审结束重新组合唯一当前 verdict。

证据重复或无法定位时仍允许作者修订：打开任务并请作者选择片段或明确整章范围，不自动猜测目标，不立即花费一次模型调用。技术报告过期问题引导重新审稿，不伪装成正文写作问题。

### P3.3 Decision Inbox

状态：**首个可用切片已完成。** 已按 project、chapter 和规范化 evidence 聚合 MemoryUpdateCandidate 与 CharacterStateChangeCandidate，Dashboard 的分散待办已合并为一个入口；所有接受动作仍调用原领域服务，不会因为 UI 聚合而自动写入长期状态。

收件箱按“正文里发生的一次故事变化”组织，而不是简单按数据库 collection 分栏。一次“角色交出钥匙”可以展开为角色状态、记忆、伏笔和时间线多个结构化变更，作者先决定这件事是否成立，再按需微调各子项。

统一覆盖：

- MemoryUpdateCandidate。
- CharacterStateChangeCandidate。
- Foreshadowing 更新。
- Timeline 候选。
- HardCanon 候选（未来可选）。

底层类型继续分离。Inbox 只提供事件级视图和共享操作语义：整体接受、拒绝、展开编辑后接受、拆分处理、撤销，以及批量处理低风险项。

批量接受必须按风险和事实确定性分组：默认只勾选正文明确发生、结构可解析且不涉及 HardCanon 的候选。高风险角色状态、重大伏笔回收、时间线不可逆变更和 HardCanon 候选默认逐项确认；若项目 policy 已明确授权 Agent 处理该范围，可以自动决定，但必须展示影响摘要并形成审计记录。候选待办本身不决定草稿采纳资格；若正文存在明确事实冲突，在同一章节决定里展示证据和影响，不能靠强迫清空收件箱解决。

组级撤销用补偿提交实现：恢复该决定涉及、且尚未被后续决定改变的字段，并留下原决定引用；不能加载旧 AppData 快照覆盖后来章节。相同证据只是分组线索，不足以把互相矛盾或先后发生的状态强行并为一条事实。结构损坏的候选仍能拒绝；无法安全应用时允许编辑修复，不制造无法清理的待办。

### P3.4 正向修订入口

作者不满意一章，未必是因为质量门禁报错。章节、阅读和修订界面都应允许直接提出创作性要求：

- 冲突不够强。
- 对白不自然。
- 人物没有做选择。
- 情绪没有到位。
- 节奏太平或太赶。
- 保留指定段落，只调整目标片段。

这类修订与 issue 驱动修订共用 revision role、对比、撤销和 RevisionCommitBundle，但不要求先制造一条质量问题。

### P3.5 可选方向探索

把“两个简短方向供选择”从远期检索阶段提前为作者闭环中的按需能力。它只在重大转折、高潮、新副本开场或作者主动请求时触发；不默认增加普通章节调用。作者也可以手写两个方向并让系统比较、合并后生成任务书。

### 验收

- 短文本修订无需进入独立修订工作台。
- 接受选区修改会形成可恢复版本。
- 从质量问题到修订候选不超过 1 次点击。
- 候选接受后立即反映在下一章上下文。
- 同一候选重复操作保持幂等。
- 合规但无聊的正文可以不依赖诊断 issue 直接进入正向修订。
- 事件级候选在 UI 中只需理解一次，底层多个状态变更仍各自可追溯。

## P4：项目级状态与小粒度持久化

### 目标

停止在普通编辑中传播和保存整份 AppData，为长篇项目和 UI/Agent 并发操作提供更清晰的数据边界。

### P4.1 Renderer Project Store

只有性能测量确认全局订阅是明显开销，且高频命令已有小粒度结果时，才在不改 AppData 数据格式的情况下引入项目级 store。候选能力包括：

- collection 级 selector。
- project scoped subscription。
- operation scoped status。
- 保存冲突和外部更新事件。

优先使用 React `useSyncExternalStore` 或轻量现有能力，不为此引入大型状态框架。

project store 不是第一步。先让命令只读取和写入关联实体，再用 store 订阅这些 compact patch；否则只是把完整 AppData 重组藏进新抽象。

### P4.2 小粒度命令

优先覆盖高频写入：

- saveChapterBody。
- upsertCharacterStateFact。
- upsertForeshadowing。
- decideMemoryCandidate。
- upsertChapterTask。
- upsertStoryDirectionGuide。
- upsertHardCanonItem。

每个命令携带 expected revision，main process 在 SQLite transaction 中执行。full save 保留给导入、恢复、设置迁移和旧 preload fallback。

SQLite 命令校验不得默认重组整份 AppData。优先读取目标 project/chapter/job 及其引用实体，让事务锁时长不会随无关项目和历史章节线性增长。

### P4.3 项目级查询

新增只读 project snapshot/digest 查询，避免每个入口总是装载所有项目全部历史。第一阶段 UI 仍可完整加载；Agent 和大型项目优先使用 scoped query。

并发交互按实际冲突处理：先保留当前全局 revision 保障；高频命令逐步改为校验目标实体版本。另一项目的无关修改不应让作者丢掉本地编辑；同一字段冲突展示当前值/本地值并允许重新提交。JSON fallback 的跨进程写入需要单写入协调或短文件锁，不能认为 renderer 队列可以覆盖另一个 CLI 进程。

### 验收

- 章节正文自动保存不执行 `DELETE FROM entities`。
- 高频命令不在事务内装载和 normalize 全库 AppData。
- 小粒度写入与 full save 共用 revision 保护。
- UI、Agent 写入后都能收到最新 revision。
- JSON export/import 继续覆盖完整 AppData。
- 旧 renderer API 仍可运行。

## P5：Agent Director Parity

### 目标

让 Codex 不读 UI 也能完成与人类导演相同的生产、审阅、修订和世界状态管理。

P5 不意味着 Agent 能力全部延后到 P4 之后。批次 C 每新增一个正式作者动作，就同步通过 P3.0 的共享命令暴露对应 Agent 能力；P5 负责补齐矩阵、范围授权、多章编排与 token 效率，而不是重新实现一套写入逻辑。

### P5.1 能力矩阵补齐

逐项核对并补齐 MCP/Tool 操作；已有接口只补行为差距，不为同一动作再增加一套命名：

- 读取和编辑 ChapterTask。
- 读取和编辑 StoryDirectionGuide。
- 读取和编辑角色卡与状态事实。
- 读取和编辑伏笔、时间线和 HardCanon。
- 接受、拒绝、编辑后接受各类候选。
- 创建修订、查看 diff、提交 RevisionCommitBundle。
- 查看和恢复版本链。
- 选择模型 profile 和 pipeline recipe。
- 执行连续多章的标准单章循环。

### P5.2 共享应用命令

UI handler 与 Agent handler 不各自实现业务规则。两者调用同一组 Application Command：

```text
preview command -> validate current revision -> apply domain service
                -> transaction commit -> return new revision + compact result
```

高风险写入不需要禁止 Agent 操作，但必须留下来源、理由、风险和 commit。项目 policy 决定哪些动作需要暂停等待人类，而不是由工具层一刀切。

实施顺序是先补共享动作，再补一份足够简单的项目授权设置，不引入复杂权限角色系统。作者可以选择“逐项确认”或“在已授权章节与内容范围内代理执行”；真正改变授权的动作仍由作者发起。范围内同类动作不重复要求人工确认，越界时只暂停需要决定的步骤，保留前序产物。当前工具对新的高风险候选接受仍是拒绝状态，单个 `confirm: true` 不是项目授权，W08 必须贯通配置、存储和 UI/Agent 后才宣称开放。

所有 commit、decision 和 candidate action 必须记录真实 actor。兼容旧数据时可以显示为 legacy/unknown，但新 Agent 写入不能标记成 user。

### P5.3 Token 效率

- 默认返回 compact digest。
- 正文、Prompt、完整报告按需读取。
- diff 优先于重复返回整章。
- 多章运行返回章节级摘要和待审队列，不累计粘贴全部历史。

### 验收

- 常规独立创作无需 Computer Use。
- UI 与 Agent 的正式写入产生相同 commit 和 version chain。
- Agent 可完成“读状态 -> 生成 -> 审稿 -> 修订 -> 决定候选 -> 提交 -> 下一章”的完整循环。
- 人类可在桌面 UI 查看 Agent 产生的全部正文、报告、决定和版本。

## P6：长篇检索与证据驱动的质量优化

### 目标

让上下文选择和 Prompt 改进从静态规则转向可验证效果，同时不建立复杂知识图谱。

### P6.1 SQLite FTS5 检索

这是 W10 测出远期召回不足后的候选方案，不是必须完成的架构升级。若现有结构化匹配已满足检索任务，则跳过 FTS。确有需要时，为以下只读文本建立可重建索引：

- chapter body/summary。
- stage summary。
- foreshadowing title/description/payoff。
- character state evidence。
- timeline title/result/impact。

FTS 只是检索候选来源，不是 canon。最终选择仍经过 ContextNeedPlan、预算和结构化优先级。

索引作为可重建派生数据维护，不用 SQLite trigger 解析任意 JSON。共享写入命令在实体提交后更新 `search_documents` / FTS；索引损坏时可以从实体重建，绝不影响正文和版本链。

中文检索先做能力实验：优先验证 FTS5 `trigram`，同时为两字人名、短规则标题和结构化 ID 提供精确匹配兜底。至少建立 30-50 条 synthetic fixture，覆盖人名、两字词、规则短语、简繁/全半角和长句；未达到召回与误报基线前不接入自动 Prompt 选择。

### P6.2 Prompt 与模型实验

为 run 记录：

- promptVersionId。
- recipeId/version。
- 各阶段模型。
- 输入/输出 token。
- 各阶段耗时。
- 首次通过、修订次数和最终接受。

增加本地对比报告：

- 不同 Prompt 版本首次通过率。
- 不同模型的平均耗时和接受率。
- 最常见修订问题。
- 每章及每千字成本。

不把 QualityGate 分数当唯一真相，最终采纳和修订行为才是最重要结果。

### P6.3 检索效果校准

用已确认的历史事实遗漏、误召回和作者最终选择校准 FTS 候选与 ContextNeedPlan 权重。不要仅凭索引命中率扩大上下文；方向探索已前移到 P3.5，不依赖 FTS 才能交付。

### 验收

- 长篇历史检索不会把全部章节塞进 Prompt。
- FTS 索引可从实体数据重建，损坏时不影响正文数据。
- 每次 run 可以追溯模型、Prompt、配方和最终结果。
- 能用真实接受数据比较至少两个 Prompt 或模型配置。

## 七、跨阶段数据兼容策略

1. 对跨进程命令、持久化 bundle、快照和不可变运行配置增加版本；普通实体沿用已有 normalize 规则，不机械扩张类型字段。
2. normalize 对旧字段给默认值，不反向改写旧记录语义。
3. 旧 14-step job 按旧 recipe 恢复；新 job 记录 recipeVersion。
4. 旧 Prompt snapshot 保持不可变，不自动套用新 block 顺序。
5. 旧报告缺 content hash 时只能显示为历史报告，不能作为当前正文已审稿或已通过的依据；显式未审稿采纳按 3.1 独立记录。
6. 完整 AppData save、JSON export/import 和 JsonStorage fallback 在 P4 后仍保留。
7. 新小粒度命令与现有 commit bundle 共用 revision 和事务规则。

每个发布候选必须跑以下兼容矩阵：

| 数据来源 | 必验行为 |
| --- | --- |
| 当前 SQLite | 加载、保存、生成、修订、提交、重启 |
| 旧 SQLite | normalize 后可读；缺新增字段不参与当前决策但不崩溃 |
| 旧 JSON | 导入、迁移前备份、写入 SQLite、再次导出 |
| 旧 job 无 `aiRunConfig` | 标记 legacy fallback，显示本次重试实际模型 |
| 旧报告无正文 hash | 仅作为历史证据，不参与当前采纳 |
| 旧 Prompt snapshot | 保持不可变；不自动套用新选择或新导向 |
| JSON fallback | bundle、commit、revision、export/import 语义继续可用 |

只给持久化协议、bundle、snapshot 和不可变 run config 增加显式版本。普通业务实体继续 normalize-on-read，避免机械地给所有记录添加 schemaVersion。

## 八、主要风险及处理

| 风险 | 处理方式 |
| --- | --- |
| 合并 AI 调用后 JSON 过大或解析不稳 | 分区 schema、部分结果容错、strict 模式保留独立调用 |
| 自适应流程跳过了必要审稿 | 由明确硬风险触发升级，并在 trace 记录跳过原因 |
| 多模型配置增加设置复杂度 | 默认继承单模型，仅高级设置展开 profile |
| Dashboard 变成另一个信息面板 | 每次只展示一个主动作和最多两个次动作 |
| Inline revision 与版本链分叉 | 所有正式应用统一走 RevisionCommitBundle |
| 小粒度写入与 full save 冲突 | 共享 revision、单一保存队列、冲突后重新读取 |
| Agent 与 UI 行为漂移 | 共用 Application Command 和同一事务服务 |
| FTS 结果被误认为事实 | FTS 仅召回，结构化账本与 HardCanon 决定权威性 |
| 指标驱动导致追求分数 | 以最终接受、修订成本和作者选择为主，不以门禁分数为唯一目标 |
| 测试数量继续膨胀 | 优先行为覆盖，淘汰已被行为测试替代的源码字符串断言 |

## 九、明确不做

本计划不包含：

- 再增加一轮通用 Novelty 关键词。
- 把每种能力继续拆成新的顶层页面。
- 为了源码行数机械拆分已经足够快的 chunk。
- 一次性把 SQLite 改成完整关系型业务模型。
- 未获项目范围授权就自动接受 HardCanon 或重大世界观候选。
- 强制每章进行双模型独立审稿。
- 新建复杂角色/伏笔知识图谱。
- 云同步、多人协作、移动端或 Web 版。
- 用新的平行系统替代现有版本链、commit bundle 或 Agent Runtime。

## 十、整体完成定义

当下列条件全部满足，可认为本轮全盘优化完成：

1. 默认标准流程以不超过 4 次逻辑模型调用为目标；任何额外调用都有明确风险理由，并能降低最终返工成本。
2. Prompt 物理顺序、声明顺序和 trace 顺序一致。
3. 作者可以从 Dashboard 一键继续当前最重要工作。
4. 流水线默认只展示四个作者阶段。
5. 选区修订和质量问题修订都能形成正式版本。
6. 所有候选可以在事件级 Inbox 中处理，并遵循人类/Agent 范围授权策略。
7. 高频编辑不再完整重写 AppData。
8. Agent 具备与 UI 对等的导演工具，并且不依赖 Computer Use。
9. 长篇检索能在固定预算内召回所需历史；只有现有召回在样本上不足时才增加 FTS，不以新增索引作为完成条件。
10. Prompt 和模型效果可以由接受率、耗时、token 与修订次数衡量。
11. 核心流程以行为测试为主，发布验证与源码契约测试职责分离。
12. Windows 安装包、SQLite、JSON 导入导出和旧项目兼容全部通过。

默认顺序为 C0 -> C1/C2 -> C3 -> C4/C5 -> C6/C7。共享接口稳定后，独立入口可以并行；不让 C1 的可选撤销功能阻塞 C2 现有修订入口验收。C0 只做当前垂直动作所需内核，不升级为通用 CRUD 框架；C1/C2 不新增 AI 调用；C3 复用现有 revision role；C4/C5 只重组交互；C6 允许修 UI，但不借机改变领域语义。

出口条件：普通章节从打开项目到继续生成不超过 2 次点击；从风险证据到局部修订不超过 1 次点击；待确认候选不会锁死草稿采纳；全部正式修改进入版本链。

### 批次 D：小粒度状态与并发安全

目标：降低长篇项目的保存成本，并让 UI 与 Agent 稳定共享同一数据源。

1. 先实现章节正文、ChapterTask、角色状态、伏笔、剧情导向和 HardCanon 的事务命令及最小读取范围。
2. 再引入订阅 compact patch 的 project-scoped store，不迁移 AppData 格式，也不把全库 normalize 简单藏进新 store。
3. 命令统一携带 expected revision，冲突返回字段级提示而非静默覆盖。
4. full save 仅用于导入、恢复、设置迁移和旧兼容。
5. 增加 project digest 与按章节查询，避免 Agent 和大项目总是加载完整历史。

出口条件：高频编辑不执行整库重写；UI/Agent 并发写入不会丢数据；冲突可恢复；JSON export/import 仍是完整数据包。

### 批次 E：Agent 导演同权

目标：Codex 通过工具完成与人类导演相同的标准单章循环，并可连续运行任意章数，但每章都必须独立计划、生成、审稿、决定和提交。

1. 将 ChapterTask、Story Direction、角色、状态事实、伏笔、时间线和 HardCanon 的读写补齐到共享应用命令。
2. 增加各类候选的接受、拒绝、编辑后接受，以及修订 diff / commit / restore。
3. Agent 使用与 UI 相同的 recipe、run profile、verdict、commit bundle 和 revision 规则。
4. 多章执行是标准单章流程的串行循环；数据冲突、提交失败或超出授权范围时暂停。已授权范围内的创作建议由 Agent 作决定并记录理由，不因普通 advisory 反复中断整批生产。
5. 默认返回 compact digest，正文、Prompt 和完整报告按需读取。

出口条件：常规创作不依赖 Computer Use；人类可在桌面 UI 查看 Agent 生成的全部正文、证据、决定和版本；同一命令重复执行保持幂等。

### 批次 F：长篇检索、效果实验与发布收口

目标：前述闭环稳定后，基于效果比较决定是否增加 FTS；发布验证则贯穿此前各批次，不推迟到本批。

1. 先测现有召回的真实缺口；只有词项检索能改善漏召回时才建立可重建的 SQLite FTS5 只读索引，否则记录“不实施新检索层”的结论。
2. 以最终采纳、修订次数、耗时和 token 比较 Prompt / 模型 / recipe。
3. 将测试拆为 unit、integration、e2e、release 四层，并淘汰被行为测试替代的源码字符串断言。
4. 建立安装包版本、native ABI、隔离 userData、SQLite 创建、导入导出和无密钥状态 smoke。
5. 更新公开文档、校验和与 GitHub Release 流程。

出口条件：检索失败不影响正文数据；实验数据不包含正文或密钥；安装包行为与开发版一致；一次命令可以完成发布前验收。

### 最近三个可发布里程碑

| 里程碑 | 包含范围 | 用户可感知结果 |
| --- | --- | --- |
| M1 可靠完成一章 | W01 + W02；R0 与批次 A 的剩余验收 | 安装版能力与开发版一致；当前正文、报告与采纳一致；接受后能继续下一章 |
| M2 更快地改好一章 | W04 + W05 交互部分；W07 随动作落地 | 问题直达局部修订；保留生成结果，对比、应用、重审和超时恢复更清楚 |
| M3 人类与 Agent 连续创作 | W03 + W06 + W07/W08 的关键同权 | 事件级候选收件箱、逐章连续生产、阅读审核、范围授权和首次成功路径完整 |

## 十二、测试与观测矩阵

```text
纯规则服务
  ├─ recipe / verdict / prompt / context / candidate policy
  └─ 相同输入稳定输出、边界和幂等

流水线集成
  ├─ fast / standard / strict / custom
  ├─ 正常、超时、取消、空响应、降级、从中间重试
  └─ 当前正文 hash、任务指纹、报告失效与最终采纳

存储集成
  ├─ GenerationRunBundle / ChapterCommit / RevisionCommit
  ├─ SQLite transaction rollback / expected revision
  └─ JSON fallback / import / export / legacy normalize

真实界面
  ├─ Dashboard 主动作
  ├─ 章节生成四阶段、诊断、候选、采纳
  ├─ 章节/阅读/修订选区重写与版本恢复
  └─ 1280×720、1440×900、窄窗口、键盘与焦点

发行产物
  ├─ Electron sandbox / CSP / preload API
  ├─ better-sqlite3 Electron ABI
  ├─ 隔离 userData 创建 SQLite
  └─ 安装、启动、导入旧 JSON、生成、重启后数据仍在
```

行为正确性是硬门禁，性能和质量使用基线观测：

| 层级 | 硬门禁 | 观测指标 |
| --- | --- | --- |
| Prompt | 无占位符、无诊断污染、权威顺序正确 | 输入 token、重复语义比例、各 block 占比 |
| Pipeline | 不误用旧产物、不重跑已成功步骤、可取消 | 端到端耗时、每步耗时、调用数、重试数；provider 无幂等保证时标明重试可能重复计费 |
| Diagnostics | 当前正文绑定、证据可定位、低置信度不硬阻断 | blocker 准确率、误报确认率、人工覆盖率 |
| Commit | 原子、幂等、版本链完整 | 冲突率、回滚次数、保存耗时 |
| UX | 主动作可达、危险操作确认、未保存状态明确 | 点击数、完成率、恢复时间 |
| Agent | UI 同权同源、compact 默认、正式写入可追溯 | Computer Use 次数、每章工具 token、暂停原因 |

每个里程碑至少选取三类脱敏章节 fixture：普通推进章、规则危机章、重大揭露章。A/B 必须固定模型、温度、任务和上下文快照；评价顺序为最终采纳与修订成本，其次是耗时和 token，质量门禁分数只作为辅助信号。

### 可重复测量方案

1. 固定 12 个可公开的合成任务：普通推进、对白/情绪、规则危机、揭露各 3 个。只在用户明确允许时使用脱敏真实稿；真实项目不作为可写测试库。
2. 先用本地 fixture 和现有 `perf:prompt`、`perf:post-draft`、`perf:novelty`、`perf:ui` 验证算法、交互与 Prompt 体积；这一步不产生远程模型费用。
3. 实施真实 provider 对照时记录模型标识、参数、时间、上下文版本和调用链，先做小样本再决定是否扩大。远程调用预算与可用模型在执行实验前明确，不在规划阶段自行调用付费接口。
4. 同一任务的 before/after 至少成对测量，必要时各重复 3 次。记录 p50/p95、失败/超时次数、真实 usage 和本地估算；小样本结果明确标注“方向性观察”，不宣称统计显著。
5. 正文匿名交叉阅读，判断是否保留、需要改几处、修改多长时间；不能用同一个质量门禁的高分单独证明质量提升。研究目标是减少一章最终采纳的总成本，不是让检查更容易通过。
6. 在隔离库建立 10/100/500 章规模，测打开、切项目、首次进入流水线、选区修订与保存；优化热点前后使用同一机器、构建模式和样本。UI 数字作观测基线，事务和版本链正确性作硬门禁。
7. 每个测试结果附日期、build/commit 标识、原始 JSON 路径和截图路径；所有 Electron/Chromium/测试服务结束后退出。只有这些证据齐全才把工作包标记为“集成已验收”。

### 每批交付清单

- 修改范围、行为变化和兼容边界；没有用新增抽象掩盖旧问题。
- 对应旅程的 before/after 操作路径和真实截图，不只给文件行数或 chunk 大小。
- 针对性行为测试、`npm.cmd run typecheck`、`npm.cmd test`、`npm.cmd run build`；文档-only 改动只需链接/编码/差异检查，不虚报完整应用测试。
- 涉及发行时额外运行 `npm.cmd run dist:win` 和 `npm.cmd run smoke:release`，检查 SQLite、preload、导入、版本与重启；报告安装包绝对路径及校验和。
- 未完成项和回退方法。配方/Prompt 改动可回到上一配置；UI 可恢复前一布局；存储迁移保留读取兼容与备份，不通过降级代码覆盖新版用户数据。

## 十三、计划治理

1. `ROADMAP.md` 只展示当前版本、下一版本和长期方向；本文保留完整依赖与施工细节。
2. 完成项进入 `CHANGELOG.md`，不在 Roadmap 中长期堆积。
3. 每个批次只允许一个主目标；结构重构与行为变化分开提交和验收。
4. 新增类型或 collection 时，同步类型、默认值、normalize、sanitize、SQLite/JSON round-trip 和 export/import 测试。
5. 新增 AI 调用必须说明不可由规则完成的原因，并纳入调用数、token、超时、取消和降级观测。
6. 新增阻断规则必须提供真实误采纳风险、证据位置和人工覆盖路径；“可能不好看”不能成为硬阻断理由。
7. UI 与 Agent 新能力优先接入共享领域服务和应用命令，禁止复制业务判断。
8. 工作树在每个发布点清理并形成可审阅提交；安装包只从通过发布门禁的 commit 构建。

Section 1.13 is the current delivery-oriented execution guide: finish one chapter reliably (M1), revise it comfortably (M2), then support continuous human/agent authorship (M3). Section 1.13 J is the current task queue, starting with integration of durable rewrite candidates, real call progress and Agent revision tools already present in source. It then covers specialised candidate decisions, task editing, author-facing UI, world-management tools and scoped authorisation. Measured persistence and retrieval improvements do not block useful UX releases. This planning update does not certify unfinished source changes or a new binary.

The latest source check confirms explicit unreviewed acceptance and edited candidate decisions already have service and UI paths. Verify them rather than rebuilding them. Sections 1.13 G-I define a field-level rebuild matrix, the human/agent parity contract and the first executable delivery checklist. Project stores and FTS remain conditional on measured bottlenecks or retrieval gaps, not mandatory migrations.

This master plan moves Novel Director from a capability-dense engineering workbench to a faster author and agent directing system. The main strategy is to reduce fixed AI calls, align prompt order with actual authority, turn the dashboard into an action-oriented command center, move short revisions into the text surface, unify pending canon decisions, introduce incremental persistence, and give the Agent API full director parity with the desktop UI.

The original dependency order was W01-W04. The current queue in section 1.13 J closes the W04/W05/W08 integration slice, then extends specialised candidate decisions and task editing. W01/W02 remain regression baselines. W07 improves the actual author journeys; W08 exposes the same operations to agents. Incremental storage and retrieval experiments follow measured needs. Existing candidate commands and editorial revision entry points need verification, not replacement.

The latest source review also found that acceptance confirmations are already combined, request controllers are keyed by run and call, and per-call cancellation is exposed through IPC/preload. Broader-than-requested revision responses are retained as candidates. These are implementation baselines to integrate and verify, not features to recreate. Author-facing request controls, candidate provenance at every caller, editable decisions, and the full in-place revision journey remain delivery targets. Sections 1.9-1.11 distinguish existing code from remaining work and define measurable end-to-end trial releases.

The next deliverables are M1 (finish a chapter reliably), M2 (revise it easily), and M3 (continuous human/agent authorship); release numbers will be assigned after verification. Preserve usable AI outputs even when automatic merging fails. Missing reviews should be distinguished from invalid writes: explicit unreviewed acceptance must retain that status instead of reusing a stale report. First-use setup should require a working model, not every worldbuilding form. Performance percentages are research targets, never reasons to remove useful model capabilities or delay independently valuable UX improvements.

The P0-P7 headings below are domain identifiers, not a new severity ranking or a requirement to reimplement finished work:

1. P0: prompt alignment and measurable baselines.
2. P1: adaptive pipeline recipes, unified post-draft analysis, and per-stage model routing.
3. P2: director command center and progressive pipeline UI.
4. P3: inline revision and a unified decision inbox.
5. P4: project-scoped state and incremental SQLite commands.
6. P5: full Agent director parity.
7. P6: outcome-based prompt/model experiments and optional FTS only when retrieval measurements justify it.
8. P7: behavior-focused tests, documentation cleanup, and release verification throughout all phases.

The plan intentionally avoids more universal guardrails, a big-bang relational rewrite, automatic canon acceptance, mandatory double review, and new top-level pages for every capability.

High-risk human approval remains the current default. Scoped agent authorization is a future author-controlled capability, not permission for an agent to approve itself. Multi-chapter production has no arbitrary two- or three-chapter cap, but each chapter completes its own review, decision and transaction before the next begins. This document update changes no application behavior and does not certify a new release.
